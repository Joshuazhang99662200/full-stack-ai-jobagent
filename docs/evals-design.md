# 链路后半段评测与 harness 自进化：设计稿

状态：已定（2026-10-20），按测试先行实现。剩下的只是 P0 期间的实测项。前序：[outreach-design.md](outreach-design.md)、[conversation-design.md](conversation-design.md)；回流原则沿用 [audit-feedback.md](../skills/job-hunting/references/audit-feedback.md)。

## 要解决什么

链路后半段指“首条招呼发出 → 对方已读 → 回复 → 要简历 / 确认意向 → 简历发出 → 约面”。每一步现在都有只追加的事件，但还没有算出过“率”，更说不清某个率为什么变了。

本设计分三层：

1. **度量**：每天按批次算漏斗指标，带样本量与置信区间；
2. **诊断**：智能体读一份确定性生成的上下文包，提出可证伪的原因假设；
3. **进化**：把诊断变成对 harness 的修改提案，人批准后生效，并按实验窗口复核，效果不好就回滚。

## 不做什么

- 不为了把指标做好看而加大发送量、放宽节奏上限或绕过审批。`OutreachPolicy` 只能收紧，进化层碰不到它。
- 指标不改证据：一次约面不能证明任何简历主张，也不能放宽质量门禁（audit-feedback.md 已定）。
- 不自动应用修改。智能体只出提案，每份提案先问后答，人批准后才生效。
- 招聘方文本只当数据。聚合与上下文包都去掉招聘方原文和个人信息，只保留分级结果。
- 不为了采“已读”去点开会话。只读消息列表预览（对应需求 E6：预览能看全的不点开）。
- 不按单个 JD 去改在线简历。在线简历只有一版三站通用的背景描述，只在数据归因到它时才改，而且有最短间隔，不来回折腾。
- 修改在线简历时，不绕过登录、验证码或风控。遇到这类页面就停下来交给人。

## 漏斗定义

计量单位是**触点**：一条 `sent` 的外联审计，或一条 `origin=self` 的对话（按 `job_id × platform` 去重）。招聘方主动来信（`origin=inbound`）单独成一条被动漏斗，不进主动漏斗的分母。

```text
S0 发出 ──► S1 送达 ──► S2 已读 ──► S3 回复 ──► S4 正向回复 ──► S5 要简历/意向确认 ──► S6 简历发出 ──► S7 约面
                          │            │
                          │            └─► 婉拒 / 不匹配（负向终态）
                          └─► 已读不回（观察窗口到期仍无来信）
未读（到期仍无已读）  ──►  SILENT
```

- 回复即视为已读：对方回了消息，就算列表上没看到“已读”也记已读。
- 已读只会从无到有：取第一次在快照里看到“已读”的时间，之后不回退。
- `duplicate_found`、`withdrawn`、`failed`、`intervention` 不进分母，归到健康指标里。

## 指标目录

### 你提的三个核心指标

| ID | 名称 | 公式 | 主要说明的问题 | 成熟期 |
|---|---|---|---|---|
| M1 | 触达率 | 已读 ÷ 发出 | 招呼开头能不能让对方点开；找岗关键词准不准（HR 活跃度、岗位是否还在招） | D+1 / D+3 |
| M2 | 已读不回率 | 已读且 2 个工作日内无来信 ÷ 已读 | 对方读了招呼、看了我方资料后觉得不合适。**主要指向三站统一的在线简历（个人背景经历描述）**，其次是选岗和招呼 | D+2 工作日 |
| M3 | 约面率 | 约面 ÷ 发出（端到端）；约面 ÷ 简历发出（条件） | 定向简历质量和对话能力 | D+14 |

全局统一用 **2 个工作日**作为“没有回音”的口径：M2 的观察窗口、对话环节的“待跟进”、未读转 SILENT 前的第一个节点，用的都是同一个数。

M2 的说明：HR 已读之后通常会点开我方资料再决定回不回，所以 M2 是在线简历最直接的结果指标。但 M2 同时受选岗和招呼影响，要把在线简历的作用单独拆出来，需要 D7（在线简历版本）和 D8（“看过我”信号），见下文。在线简历由智能体负责改写和执行，人只批准上线哪一版，见“在线简历飞轮”。

### 扩展指标（可选）

**找岗层**（用来判断关键词准不准）

| ID | 名称 | 公式 / 口径 |
|---|---|---|
| J1 | 关键词产出率 | 某搜索词带来的入库数 → 过硬过滤 → strong/medium 档占比 |
| J2 | 关键词下游转化 | 某词带来的发出中，已读 / 回复 / 约面的比例 |
| J3 | 硬过滤淘汰率、invalid 隔离率、去重率 | 按来源和搜索词分 |
| J4 | JD 新鲜度 | 从 `published_at` 到发出的天数，按桶看 M1（老岗位往往 HR 已不活跃） |

**招呼层**

| ID | 名称 | 公式 / 口径 |
|---|---|---|
| G1 | 送达率 | 送达 ÷ 发出。平台健康度；突然下降先怀疑平台，不怀疑文案 |
| G2 | 首回率 | 回复 ÷ 发出 |
| G3 | 正向回复率 | L1/L2 且非婉拒 ÷ 回复 |
| G4 | 婉拒率、不匹配率 | 婉拒 ÷ 回复；mismatch ÷ 回复 |
| G5 | 首回时延 | 发出到第一条来信的中位数（工作小时） |
| G6 | 跟进挽回率 | 跟进之后才回复的 ÷ 跟进条数 |
| G7 | 招呼退回率 | `draft-batch` 退回 ÷ 起草条数，按退回原因分。反映起草和规则的一致程度 |
| G8 | 人工否决率 | 1 − 批准编号数 ÷ 清单条数。**人和智能体判断不一致的最直接信号** |

**对话层**

| ID | 名称 | 公式 / 口径 |
|---|---|---|
| C1 | 要简历率 | 进入 RESUME_REQUESTED ÷ 回复 |
| C2 | 简历交付时延 | RESUME_REQUESTED 到 RESUME_SENT 的工作小时 |
| C3 | 简历后回复率 | 简历发出后有来信 ÷ 简历发出 |
| C4 | 回复审批通过率 | 获批回复 ÷ 起草回复；人工改写比例（需新增埋点，见下） |
| C5 | L3 交人时延 | L3 / 危险来信到人处理的时间 |
| C6 | 被动来信质量 | 被动来信里不匹配的比例；被动来信转约面率 |

**护栏指标**（只能守住，不能拿来换增长）

| ID | 名称 |
|---|---|
| H1 | 每站每日 `intervention` / `failed` 次数、叫停天数 |
| H2 | 每日上限利用率（只用来看容量，不作为越高越好的目标） |
| H3 | STALE_APPROVAL 次数 |
| H4 | 巡检准点率、中断后续跑次数 |
| H5 | 证据与确定性检查违规：必须为 0 |

**成本**（可选）：每次约面对应的发出条数、子代理运行次数。

## 统计口径

- **按发出日分批，不按事件日。** “每天的触达率”指当天发出那一批在 D+k 时的已读比例。没到成熟期的批次标“未成熟”，不显示一个偏低的数字。
- **可观测性按平台声明。** 在 `sources/*.yaml` 增加 `observability.read_receipt`。已知 Boss 和智联的列表预览带“[送达] / [已读]”前缀；猎聘待实测。看不到已读的平台，M1/M2 显示 N/A，不显示 0。
- **小样本必须带区间。** 现在每站每天约 15–30 条，日度比率噪声很大。每个值都输出 `n` 和 Wilson 95% 区间；n < 30 的切片标“样本不足”，不参与归因。默认看 7 天滚动，日度只做明细。
- **周几效应。** 周末和周五下午的已读本来就低，比较时按周几对齐，或者用同期对照。
- **组成效应。** 总体指标变化 = 各切片内部的变化 + 切片占比的变化（例如 Boss 的占比上去了）。诊断时先做这一步拆分，避免辛普森悖论。

## 数据缺口：先补埋点

不补这几项，前面的指标有一半算不出来，归因也无从做起。

| # | 缺口 | 现状 | 补法 |
|---|---|---|---|

## 架构

```text
L0 事件层  outreach_audits / conversation_events / patrol_snapshots / provenance  （已有 + D1–D6）
   │  纯函数，确定性
   ▼
L1 指标层  jobagent.evals：漏斗、指标、切片、区间 → eval_snapshots（只追加，带口径摘要）
   │  确定性检测
   ▼
L2 诊断层  MetricShift（显著变化）→ 上下文包 → 智能体写 Diagnosis（假设 + 引用 + 可证伪预测）
   │
   ▼
L3 进化层  HarnessProposal → 先问后答 → 人批准 → 新 harness 版本 → 实验窗口 → 复核：保留 / 回滚
   │
   └──────────────► 回到 L0，继续观察
```

按 AGENTS.md 的边界，`jobagent/evals/` 是领域模块，只依赖契约，不碰 Typer、SQLite 和浏览器。存储层另写 repository，CLI 做薄封装。

### L1 指标层

- 契约放在新增的 `schemas/evals.py`：`MetricDefinition`（ID、分子、分母、成熟期、适用平台）、`FunnelCohort`、`MetricValue`（值、n、区间下限、区间上限、状态：ok / immature / unobservable / insufficient）、`Breakdown`。
- 切片维度：平台、发出日、周几、match_tier、search_term、variant、hook_requirement、harness_version、profile_version、JD 新鲜度桶、公司规模、薪资带。
- 有了 D8 之后，M2 还能拆成两段：已读后看过资料却不回（指向在线简历），以及已读后没看资料也不回（指向招呼和选岗）。
- 指标定义写在代码注册表里，新增或修改指标要走代码评审。定义取摘要；`eval_snapshots` 只追加并记录口径摘要，口径变了也不会改写历史。
- **智能体不自己算比率。** 所有数字都从工具里取，避免模型心算出错或编出数字。

### L2 诊断层

**变化检测（确定性）**：当前窗口和基线（前 14 天、周几对齐）比较，区间不重叠且两边 n 都达标，才产出 `MetricShift`。

**排查顺序**（写进诊断策略，按顺序排除）：

1. **测量问题**：快照覆盖率掉了？“已读”解析命中数突变？巡检漏跑？
2. **平台问题**：送达率（G1）掉了？有 intervention？平台改版？
3. **外部因素**：节假日、周几、招聘季。
4. **组成变化**：平台、档位、搜索词的占比变了吗？用上面的组成拆分。
5. 排除了前四项，才归因到**策略**：招呼变体、harness 版本、选岗规则、在线简历版本。M2 异常时先看 profile_version 前后有没有断点，再看 D8 拆分的两段哪一段在动。

**`Diagnosis` 契约**：每条假设必须

- 引用上下文包里实际存在的切片 ID 和 n（仓库校验，引用不存在的切片会被拒）；
- 给出可证伪预测，例如“如果是关键词 X 的问题，那么 X 以外的切片 M1 应该不变”；
- 标注所属排查层级（1–5）。

### L3 进化层

**可进化面分三级**，提案只能指向白名单内的位置，由仓库按路径和键名校验：

| 级别 | 可改什么 | 生效方式 |
|---|---|---|
| A | 搜索词增删和优先级（filter_context 的主题与检索顺序）、档位内的排序偏好权重、招呼开头 / hook 的选取策略（message-generation.md 里非确定性的部分）、跟进时机（在设计稿给的范围内）、巡检时间窗 | 提案 → 先问后答 → 人批准 → 生效 |
| P（公开内容） | 三站统一的在线简历（个人背景经历描述） | 智能体归因、改写、复核，人批准这一版的摘要；智能体在浏览器里执行，回读核对后登记版本。见“在线简历飞轮” |
| B | 新指标、新埋点、更严的确定性检查 | 提案只算需求，按测试先行走代码评审 |
| C | 证据规则、审批门禁、`OutreachPolicy` 放宽、首条招呼确定性检查放宽、AGENTS.md 硬边界 | **不可进化**，提案直接被拒 |

### 在线简历飞轮

在线简历是三站 HR 都会看到的公开内容。飞轮里的每一步都由智能体完成，人只在“上线哪一版”这一步做决定。

```text
① 快照  巡检时只读抓取三站在线简历 → profile_snapshots → 有变化就生成 profile_version
   │
② 归因  M2 出现 MetricShift → 按排查顺序 1–5 走完 → 落到“在线简历”这一层才继续
   │     （判据：D8 拆出的“看过资料却不回”在动，选岗和招呼两段都没动）
   ▼
③ 改写  optimizer 管线：base 由已确认证据生成 → 改写 → 独立复核 → 校验
   │     每条主张引用 EVID_*，不写自证句，不超出证据范围；按各站字段和字数上限分别排版
   ▼
④ 提问  profile ask：逐字段 diff、依据的切片与 n、预期 M2、观察窗口、条件回滚
   │     人回答“同意 / 不同意 / 只改某几段”，原话逐字存档，审批绑定这一版的摘要
   ▼
⑤ 执行  profile gate 放行（持有站点租约、审批有效、离上次修改满最短间隔、该站当天没被叫停）
   │     → 智能体在本机 Chrome 里逐站逐字段填入获批原文 → 保存
   │     → 立刻回读快照，逐字段核对摘要：一致才记 applied；不一致或遇到验证、风控就记 intervention，交人
   ▼
⑥ 观察  以生效时刻为界分批累积 M2（含 D8 拆分）、M1、C1、M3；对齐周几
   │     观察期内暂停 A 级招呼实验，同一时间只变一个量
   ▼
⑦ 判定  复核：显著改善 → 保留，成为冠军版本
   │          显著变差，或到期仍未达到回滚条件 → 回滚到上一个冠军版本
   │          区间重叠 → 延长一个窗口；第二次仍不显著，按“没有效果”处理
   ▼
⑧ 收口  见下文；收口后飞轮停转，等新的 MetricShift 再归因到在线简历时才重开
```

**执行通道**：用 Claude in Chrome 操作本机已登录的 Chrome（和巡检同一通道）。桌面级的 computer use 对浏览器只有读取权限，点不了也输入不了，所以不用它来改网页。三站各自的字段名、页面路径和字数上限写在 `sources/*.yaml`，由实测确定，不靠猜。

**节奏与护栏**：

- 两次上线之间至少隔一个完整的观察窗口：默认 10 个工作日，并且“已读”事件要累积到 n ≥ 60 才能判定，取两者中较晚的那个。
- 同一时间只允许一版处在观察中；每个季度最多上线 4 版。
- 提问时一并列出条件回滚：回滚目标是上一个已经获批并上线过的冠军版本，回滚条件写成确定性规则。人批准这一版，就同时批准了“满足条件时回滚”；判定由 `evals review` 按规则算出，不由智能体主观决定。除此之外的任何改动都要重新提问。
- 快照发现 `external` 变化（本人或平台改的）时，当前观察窗口标为“混杂”，暂停判定。
- 指标再好看，也不能成为放宽证据门禁的理由。证据之外的主张一律不写。

**收口**：满足下面任一条，在线简历就进入“已收口”，锁定冠军版本：

- 连续 2 版都不显著，说明这一层的可改进空间已经吃完；
- M2 的“看过资料却不回”这一段已经降到和基线同组岗位相当的水平（阈值在第一次收口前，按积累的基线数据定）；
- 本季度的版本额度已用完。

收口后，冠军版本和每一版的结论（包括被否掉的写法）都写进经验记忆。只有新的 MetricShift 再次归因到在线简历时，才会重开飞轮。

**`HarnessProposal` 契约**：编号、级别、目标（文件 + 键名）、diff、依据（eval_snapshot 编号、Diagnosis 编号、n）、预期效果（看哪个指标、预期方向和幅度）、观察窗口、回滚条件、修改前的 harness 版本。审批沿用外联的纪律：提问必须先于答复，答复绑定提案摘要，人的原话逐字存档。

**实验设计**：

- 优先**同期交替**而不是前后对比：同一天里按 `hash(job_id)` 确定性地分到 A / B 变体，抵消周几和招聘季的影响。每一条招呼照样逐条经人审批，变体只是一个标签。
- 一次只改一个变量。
- 样本量要实话实说：已读率从 40% 提到 55%，80% 功效下每组大约需要 170 条。按每天 30 条一分为二，要 12 天左右。所以只测预期效果大的改动；首回率基数更低，需要的样本更多。
- 到期后 `evals review` 给出结论：保留 / 回滚 / 延长观察。回滚同样需要人确认。

## 上下文传参

上下文包由 `jobagent evals context` 确定性生成，和技能树一样分层、按需加载：

| 层 | 内容 | 体量 | 何时加载 |
|---|---|---|---|
| P0 | 当日主指标（带 n、区间、状态）、护栏状态、进行中的实验、待批提案 | ~1–2k tokens | 每次巡检收尾 |
| P1 | 被标出变化的那几个指标的切片明细 | 按需 | 诊断时 |
| P2 | 样本级行：job_id、平台、档位、搜索词、变体、阶段时间线；我方招呼原文（这是我们自己的文本） | 按需 | 诊断招呼问题时 |

- 招聘方原文和姓名不进任何一层，只给分级与标记（level、asks_resume、interview_invite、declined）。这样既防提示注入，也守隐私。
- 每个包带 `data_as_of`、`definition_digest`、`pack_digest`。Diagnosis 和 Proposal 必须写明自己依据的 `pack_digest`，仓库据此核对引用。
- 分工沿用现有约定（记忆“Agent division of labor”）：读快照、采已读状态交给 Sonnet 子代理；诊断和写提案由主会话完成。

## 工具设计

CLI（确定性，全部输出 JSON，全部登记进能力目录）：

| 命令 | 作用 |
|---|---|
| `evals snapshot` | 当日物化，写入 `eval_snapshots`；巡检收尾时调用 |
| `evals funnel --from --to --platform --by DIM` | 分批漏斗 |
| `evals metric M1 --by search_term --window 14d` | 单指标切片 |
| `evals shifts` | 列出显著变化 |
| `evals context --purpose daily\|diagnose\|review [--shift ID]` | 生成上下文包 |
| `evals record-diagnosis diag.json` | 校验引用后存档 |
| `evals propose proposal.json` | 校验白名单后存档 |
| `evals ask-proposal` / `evals approve-proposal --request --answer` | 先问后答 |
| `evals assign --batch` | 给批次确定性分配实验变体 |
| `evals review PROPOSAL_ID` | 实验复核；在线简历版本按条件回滚规则判定 |
| `profile snapshot record snap.json` | 存一份在线简历快照，和上一份做 diff，有变化就生成版本 |
| `profile propose --from-diagnosis DIAG_ID` | 校验诊断确实归因到在线简历层；把 optimizer 产出的改写打成待上线版本 |
| `profile ask` / `profile approve --request --answer` | 先问后答，审批绑定版本摘要和条件回滚规则 |
| `profile gate --platform --session` | 放行前复核：租约、审批有效、最短间隔、当天没被叫停、没有别的版本在观察 |
| `profile record --platform --result applied\|failed\|intervention` | 记账；`applied` 之前必须先有回读快照，并且摘要一致 |

MCP 中继（给 Cowork 用，只读）：`funnel_today`、`metric_shifts`、`open_proposals`。所有写操作都留在主会话的 CLI 里。

## 记忆设计

| 层 | 存什么 | 存在哪 | 写入规则 |
|---|---|---|---|
| 事实 | 事件、指标快照、诊断、提案、实验 | 本地 SQLite，只追加 | 工具写，可重放 |
| 经验 | 被实验验证过的结论，例如“Boss 周五 16 点后发出的已读率显著偏低（n、区间）” | `eval_insights` 表（私有，不进仓库） | **只有实验复核后**才能写入；每条带证据、适用范围、复验日期，过期或平台行为变了就降级为待复验 |
| 反例 | 被否掉的假设、被回滚的提案及原因 | 同上 | 防止智能体反复提同一个失败的主意 |
| 冠军 | 在线简历的当前冠军版本、历次版本的结论、收口状态 | `profile_versions` + `eval_insights` | 只有 `evals review` 能改冠军；收口状态通过 P0 层注入每次的上下文 |
| 偏好 | 用户对工作方式的要求 | Claude 自动记忆 | 不存指标，指标会过时 |

经验记忆通过 `evals context` 的 P0 层注入，不写进 `skills/`：这些是个人求职数据，不该进仓库。

## 闭环示例

> Boss 的 7 日 M1 从 48% 掉到 30%（两边 n 都 > 60，区间不重叠）→ `MetricShift`。
>
> 1. 测量：快照覆盖率正常，“[已读]”解析命中数没有突变 → 排除。
> 2. 平台：G1 送达率 98%，没有 intervention → 排除。
> 3. 外部：对齐周几后仍然下降 → 排除。
> 4. 组成：搜索词“AI 产品经理 金融”的占比从 20% 升到 60%，而它切片内的 M1 一直在 25% 左右；其他词切片内基本不变 → **是组成效应**。
>
> 诊断：已读率下降来自关键词组合的变化，不是招呼写差了。可证伪预测：去掉这个词之后，总体 M1 应回到 45% 上下。
>
> 提案（A 级）：在 filter_context 里把这个词降到检索顺序末位；观察 7 天；回滚条件是总体 M1 没有回到 40% 以上。→ 问人 → 批准 → 新版本 → 复核。
