# 评测 P1：指标层详细设计

状态：草案（2026-10-21），待评审。上位设计见 [evals-design.md](evals-design.md)，P0 埋点已在 `7dea91e` 落地。

## 要解决什么

把已有的事件和回执算成按发出批次的漏斗指标。每个数都带样本量、区间和状态；看不到的就说看不到，不把“没看到”当成“没有”。

P1 只读数据、只算数，不做诊断，不出提案，不碰任何审批或发送路径。

## 现状数据（2026-10-21，只读盘点）

| 项 | Boss | 猎聘 | 智联 |
|---|---|---|---|
| 首条招呼 `sent` | 70 | 11 | 1 |
| 已读回执 / 送达回执 | 10 / 16 | 2 / 3 | 0 / 1（已读不可观测） |
| 消息页快照 | 39 | 15 | 24 |

- 全库：约面 2 个，要简历 4 个，婉拒 4 个；来信分级 L1 12、L2 5、L3 2、不匹配 5。
- 检索词命中只有 22 个职位、4 个词，因为 P0 刚开始采集。在线简历快照还没有。

结论：Boss 的 M1 一旦成熟，样本量就够出结论；猎聘暂时只能看明细；智联只能算送达和回复。J 类（关键词）指标要等采集积累，历史部分记为“未采集”。

## 计量单位：触点

一个触点是一次到达招聘方的我方首次接触：

| 来源 | 发出时刻 | 对应的对话 |
|---|---|---|
| `outreach_audits.result = sent` | `recorded_at` | `conversation_id_for(platform, job_id)`，确定性推出 |
| `conversations.origin = self` | `opened_at` | 本身 |

- 招聘方主动来信（`origin = inbound`）不是触点，进单独的被动漏斗。
- `duplicate_found`、`withdrawn`、`failed`、`intervention` 不是触点，计入护栏指标。
- 有 `sent` 审计但没有对应对话（`sync-outreach` 没跑），这个触点照样计入分母，后续结果记 `unknown`，并计入覆盖率 K2。

批次日期按平台日历日（UTC+8，与 `PLATFORM_DAY` 一致）取发出时刻的日期。

## 触点时间线

`build_timelines(...)` 是一个纯函数：输入审计、对话、对话事件、全部消息页快照、检索词命中、在线简历版本、巡检完工记录，以及各站的可观测性声明；输出每个触点一条 `ContactTimeline`。

| 字段 | 取法 |
|---|---|
| `sent_at` | 见上表 |
| `sightings` | 重放全部快照，对每份快照调用 `receipts_from_snapshot`，得到每次看到的状态（不只首次） |
| `delivered_at` | 第一次看到 delivered 或 read 的快照时间 |
| `read_at` | 第一次看到 read 的快照时间；如果更早就有来信，取来信时间，并标 `read_implied` |
| `first_reply_at` | 第一条 INBOUND 事件 |
| `positive_reply` | 第一条来信是 L1/L2，且没有婉拒 |
| `resume_requested_at` / `intent_at` / `resume_sent_at` / `interview_at` | 第一次进入对应阶段（INTERVIEW 由 L3 或约面标记触发） |
| `terminal` | DECLINED / CLOSED（不匹配）/ SILENT，及其时间 |
| 维度 | 平台、match_tier、variant、hook_requirement、experiment_id、harness_version；首触检索词（`sent_at` 之前最早的命中）；发出时生效的 profile_version；周几、发出时段、JD 新鲜度桶 |

`read_at` 是“第一次被我们看到已读”的时间，只会晚于真实已读时间，不会早。所有和已读相关的时延都带这个偏差，文档和输出里都注明。

## 判定规则：四种状态

每个触点在每个指标上只有四种状态之一：

| 状态 | 含义 |
|---|---|
| `hit` | 发生了 |
| `miss` | 窗口到期，并且有证据表明没发生 |
| `pending` | 窗口还没到期 |
| `unknown` | 窗口到期，但没有证据判断。另有 `unobservable`：平台不支持观测这一项 |

“没有证据”就是 `unknown`，**绝不记成 `miss`**。具体到三个核心事件：

- **未读（M1 的 miss）**：在 `sent_at + 2 个工作日` 之后，存在一份该站快照看到这个触点仍是 delivered，并且此前没有 read，也没有来信。只是在快照里没出现（滚出了列表、匹配不上），一律记 `unknown`。
- **已读不回（M2 的 hit）**：已读，且 `read_at + 2 个工作日` 之后至少有一次完工的巡检，而这段时间里没有来信。窗口里如果一次完工巡检都没有，记 `unknown`，因为可能只是没去读消息。
- **未约面（M3 的 miss）**：`sent_at + 10 个工作日` 之后有完工巡检，并且没有进入 INTERVIEW。

工作日沿用 `workdays_between` 的口径。“2 个工作日”全局统一（见 evals-design.md 已定事项 1）。

## 指标定义

指标定义写在代码注册表里（`jobagent/evals/metrics.py`），每条定义取摘要，所有定义合起来再取一个 `definition_digest`。

| ID | 分子 | 分母 | 成熟期 | 适用 |
|---|---|---|---|---|
| M1 触达率 | 已读 hit | hit + miss | D+2 工作日 | 声明了 read_markers 的站 |
| M2 已读不回率 | 已读不回 hit | 已读且窗口有结论的 | 已读 +2 工作日 | 同上 |
| M3 约面率 | 约面 hit | hit + miss | D+10 工作日 | 全部 |
| M3c 简历后约面率 | 约面 | 简历已发出且窗口有结论的 | 简历 +10 工作日 | 全部 |
| G1 送达率 | delivered hit | 有快照结论的 | D+2 工作日 | 声明了任一标记的站 |
| G2 首回率 | 有来信 | 有结论的 | D+2 工作日 | 全部 |
| G3 正向回复率 | positive_reply | 有来信的 | — | 全部 |
| G4 婉拒率 / 不匹配率 | DECLINED / CLOSED（不匹配） | 有来信的 | — | 全部 |
| G5 首回时延 | 中位数和四分位（工作小时） | 有来信的 | — | 全部 |
| G6 跟进挽回率 | 跟进之后才有来信 | 发过跟进的 | 跟进 +2 工作日 | 全部 |
| G8 人工否决率 | 1 − 批准编号数 ÷ 清单条数 | 按批次 | — | 全部 |
| C1 要简历率 | RESUME_REQUESTED | 有来信的 | — | 全部 |
| C2 简历交付时延 | 中位数（工作小时） | 简历已发出的 | — | 全部 |
| J1 / J2 检索词产出与转化 | 按首触检索词切 M1、G2、M3 | 有首触检索词的触点 | 同各指标 | 全部 |
| H1 护栏 | 每站每日 intervention / failed 次数 | — | — | 全部 |
| K1 回执覆盖率 | 有任一 sighting 的触点 | 声明了标记的站的触点 | — | 测量健康 |
| K2 同步率 | 有对应对话的触点 | 全部触点 | — | 测量健康 |
| K3 检索词覆盖率 | 有首触检索词的触点 | 全部触点 | — | 测量健康 |
| K4 unknown 占比 | 各指标里的 unknown | 到期的 | — | 测量健康 |

K 类是 P2 排查第一层“测量问题”的直接依据。K1 或 K4 突变时，先怀疑采集，再怀疑策略。

## 统计

- 每个比率都输出 `n`（分母）、`value` 和 Wilson 95% 区间，并给一个状态：
  - n ≥ 30：`ok`
  - 10 ≤ n < 30：`insufficient`，照样显示，但不参与 P2 归因
  - n < 10：只给计数，不给比率
  - 窗口未到期：`immature`
  - 平台不支持：`unobservable`
- 时延类指标输出中位数和四分位，n < 10 时只给计数。
- 日报按发出日列每天一行，另给 7 天滚动值，滚动窗口同样按发出日。
- 所有输出都带 `as_of`、`definition_digest`，以及纳入计算的事件截止时间，同一输入总能得到同一输出。

## 契约（新增到 `schemas/evals.py`）

| 名称 | 要点 |
|---|---|
| `MetricId` | 上表 ID 的枚举 |
| `MetricDefinition` | ID、分子 / 分母的事件名、成熟期（工作日）、适用条件（需要哪种可观测性）、说明 |
| `OutcomeState` | hit / miss / pending / unknown / unobservable |
| `ContactTimeline` | 触点键（平台 + job_id 或 conversation_id）、时间线字段、`sightings` 计数、维度、各指标的 `OutcomeState` |
| `MetricValue` | 指标、切片键、n、value、区间、状态、各状态计数 |
| `FunnelReport` | as_of、窗口、`definition_digest`、按发出日的行、滚动值、K 类健康指标 |
| `EvalSnapshot` | 某天的 `FunnelReport` 物化结果，只追加 |

时间线和报告里只放 ID、计数、时间和标签，不放招聘方姓名、消息原文或在线简历正文。

## 存储

一张新表 `eval_snapshots`（`snapshot_id`、`as_of`、`definition_digest`、`report_json`），只追加。迁移号在实现时取当时的下一个（工作区里另有未提交的 0011 / 0012）。

时间线不落库：每次从事件重放，保证口径改了之后历史也能用新口径重算。物化快照只用来看趋势，并保留当时的口径摘要。

## 命令

| 命令 | 作用 |
|---|---|
| `evals funnel --from --to [--platform] [--by DIM] [--as-of]` | 按发出日的漏斗，可按一个维度切 |
| `evals metric ID --window 14d [--by DIM]` | 单指标切片，用于诊断 |
| `evals contacts [--platform] [--state ID=unknown]` | 触点明细（只有 ID、时间和标签），用来排查 unknown |
| `evals snapshot [--as-of]` | 物化当天报告，巡检收尾时调用 |

全部输出 JSON，全部登记进能力目录。MCP 中继后续加只读的 `funnel_today`。

## 测试计划（测试先行）

1. 触点：sent 计入；duplicate、withdrawn、failed、intervention 不计；self 计入；inbound 不计；没同步的照样计入，结果为 unknown。
2. 回执重放：同一触点多次看到；先 delivered 后 read；来信早于 read 时 `read_implied`。
3. 四种状态：到期且之后有 delivered 的观测才算 miss；滚出列表算 unknown；智联已读为 unobservable；窗口里没有完工巡检时 M2 为 unknown。
4. 工作日窗口跨周末，以及 UTC+8 的日期边界。
5. Wilson 区间的已知值，以及 n 的分档阈值。
6. 维度：首触检索词取 `sent_at` 之前最早的命中；profile_version 取发出时生效的版本，都没有时为 unknown。
7. 同一输入同一输出：结果与输入顺序无关，`definition_digest` 稳定。
8. CLI：输出里不出现姓名、公司名或原文。

## 在线简历两阶段对比（2026-10-21 起）

用户 10/21 确认执行一次在线简历修改：改之前先把三站当前内容存成快照，然后以修改时刻为界分成两个阶段做对比。

### 为什么是两阶段，而不是同期 A/B

每个站只有一份在线简历，同一时刻所有 HR 看到的都是同一版，做不了同期分组。分站错峰（先改一个站）也不可行：三站要保持一致，而且猎聘、智联的样本太少，当不了对照组。所以采用**前后两阶段对比**，用下面几条规则尽量把其他因素排除掉。

### 阶段按曝光时刻划分，不按发出时刻

HR 是在读到招呼、点开资料时才看到在线简历。昨天发出、今天改完之后才读的那条，看到的是新版本。所以：

| 指标 | 分阶段依据 | 理由 |
|---|---|---|
| M2 已读不回率（主指标） | 已读时刻所在的版本 | 读的时候看的是哪一版，就算哪一版 |
| G2 首回率（辅助） | 已读时刻所在的版本；没读到的不计 | 同上 |
| M1 触达率 | 发出时刻 | 已读之前看不到资料，M1 只当对照：两阶段 M1 应基本不变，变了说明招呼或选岗也变了 |
| D8 “看过我”（猎聘、智联） | 页面显示的查看时间 | 直接就是曝光时刻 |

`read_at` 是第一次在快照里看到已读的时间，真实已读时间落在“上一份快照，`read_at`]”这个区间里。如果修改时刻落在这个区间内，这个触点归哪一阶段说不清，**两个阶段都不计**，单独列为跨界样本。

每个站用自己那一版的生效时刻（回读核对通过的时间）作为分界，三站不共用一个时间点。

### 两阶段之间必须保持不变的东西

阶段 B 的观察期内，以下内容冻结。确实改了的，对比按 `harness_version` 分层，并在结论里注明“混杂”：

- 招呼写法（greeting_style、message-generation.md）；
- 检索词与筛选配置（filter_context.json，10/21 19:44 刚改过一次）；
- 不开 A 级招呼实验。

阶段 A 的样本本身就混着 10/20 招呼写法的调整，所以 A 期只取与 B 期同一 `harness_version` 的部分作为主比较；取不到足够样本时，用全部 A 期样本作为次比较，结论降级为参考。

### 事先定好的判定规则

为了避免看到数据再挑口径，判定规则在上线前写定，并计入审批摘要：

- 主指标：M2（按曝光分阶段），平台 Boss；猎聘、智联只看明细。
- 观察期：阶段 B 至少 10 个工作日，并且 B 期“已读”样本 n ≥ 30，取两者中较晚的。
- 判定：两阶段的 M2 用 Fisher 精确检验，并报告各自的 Wilson 区间。
  - B 期显著更低 → 保留新版本；
  - 显著更高 → 回滚到快照留存的旧版本；
  - 不显著 → 延长一个观察期，第二次仍不显著，按“没有效果”处理并保留现状。
- 实话实说：A 期截至 10/21 只有 12 条已读，样本很薄，这一轮大概率只能检出很大的差异。所以结论要连同样本量一起汇报，不把“不显著”说成“没区别”。

### 需要的记录

- 修改前快照：已于 10/21 20:04–20:08 只读抓取并入库，三站各生成一个 baseline 版本（Boss `PROFVER_05AC5E0D9918A5EC`，22 段；猎聘 `PROFVER_E7368E475363F0D0`，9 段；智联 `PROFVER_787AD66969B3AACF`，11 段）。原文只存在本地私有库和 `candidate/private/profile/`。
  - 抓取时发现三站内容并不一致：Boss 与智联基本是同一版，猎聘是另一版。所以 A 期的基线按站分别记，不能假设三站同版。
  - `work_header#n` / `project_header#n` 是抓取时拼出来的“公司｜职位｜起止时间”，不是平台上的可编辑原文；智联有两处页面没显示的项填了占位说明。回读时必须用同样的拼法，否则摘要对不上。
- 修改后的回读快照：生成新版本。这个版本应标记为 `agent`，并关联到人的批准；P0 只能生成 `external`，所以要先补 P4 的最小集合（提案、提问、批准，以及回读摘要必须与获批摘要一致的登记），再在平台上执行修改。
- P1 的 `ContactTimeline` 增加 `exposure_version`（已读时刻所在的在线简历版本）和 `crossover`（是否为跨界样本）两个字段，`evals funnel --by exposure_version` 直接给出两阶段对比。

## 不做什么

- 不推断：没有回执就不判未读，没有巡检就不判未回。
- 不在 P1 里解释原因，不比较版本，不出提案。这些是 P2 / P3 的事。
- 不给任何指标设目标值，也不把指标接到发送节奏上。
