# 可分发的求职 Harness Skill 设计与验收

日期：2026-10-08。状态：用户已批准；第一阶段本地代码与合成验收完成，2026-10-20 随外联与巡检一起提交。

## 用户目标

用户从 GitHub 安装一个 skill 后，在 Codex 或 Claude Code 中用自然语言启动求职工作。宿主承担推理、工具调用与用户交互；本项目提供可安装的操作协议、任务状态、渐进加载的技能树、确定性领域服务和审批门禁。

预期体验：首次配置个人工作区 → 导入与确认候选人证据 → 找到匹配岗位 → 用户选择岗位 → 按完整 JD 定向生成简历 → 产出并检查 PDF → 用户逐份确认投递包 → 在支持的平台提交一份申请 → 汇总实际结果。用户选择了岗位，不等于批准发送简历或联系招聘方。

截图仅为体验参考。其中的每天 10 点、具体平台账户、六份投递和招聘方消息不构成本项目的操作授权，也不作为默认配置。

## 方案选择

1. **推荐：共享 skill 核心与两种宿主的薄适配。** 复用现有领域服务和 `skills/job-hunting/`，增加可分发资源、初始化、任务恢复和宿主能力探测。确定性逻辑留在 Python；推理复用宿主。能兼顾 GitHub 安装和稳定执行，工程范围适中。
2. **纯 Markdown skill。** 最容易安装，但依赖、状态、审批和恢复由模型自行维持，难以满足可靠性与现有证据契约。
3. **独立常驻进程与自建界面。** 可以控制完整运行环境，但安装、运行成本与安全边界明显扩大，第一阶段不采用。

这里的 harness 是可分发的工作协议和控制层；模型微调不在本次范围内。

## 包装与安装

- `skills/job-hunting/` 继续作为技能、策略和来源清单的权威来源，保留 optimizer 嵌套路由，避免复制两套正文。
- 发布包提供 `SKILL.md`、references、来源清单、初始化脚本、宿主适配说明和运行时清单。
- Python 运行时和 skill 资源使用同一版本。发布构建产生独立安装包；清单记录版本、来源 revision 与资源 SHA-256。安装复制的是完整构建包，包含匹配 runtime，不能假设宿主机器已有 `jobagent`。从 GitHub 源码只复制 `skills/job-hunting/` 无法满足运行依赖，首次调用明确停止并给出完整 checkout 构建命令；不自动下载或执行未知版本代码。
- Codex 与 Claude Code 分别采用其官方支持的 skill 安装位置或插件加载方式。安装不能依赖开发者本机的绝对路径、全局技能或秘密配置。
- 初始化仅在用户调用本 skill 时发生。加载元数据不启动搜索、不登录、不发送、不创建计划任务。
- Python、平台 CLI、PDF 渲染器等依赖先探测，再列出所需安装及版本；不覆盖用户已有环境、宿主设置或其他 skill。
- 安装的代码目录保持只读使用。候选人数据、产物和运行状态写入用户选择的独立工作区。

## 启动与恢复

自然语言命中或显式调用 skill 后，依次：识别宿主与当前能力 → 检查匹配的 runtime → 选择或初始化工作区 → 读取活动任务 → 输出当前状态与下一步 → 加载本步骤需要的策略和契约 → 执行已获授权的能力。

统一状态包括 `NEW`、`RUNNING`、`WAITING_FOR_FACT_CONFIRMATION`、`WAITING_FOR_JOB_SELECTION`、`WAITING_FOR_REVIEW`、`WAITING_FOR_APPROVAL`、`WAITING_FOR_LOGIN`、`DELIVERY_OUTCOME_UNKNOWN`、`COMPLETED`、`FAILED`、`CANCELLED`。领域结果继续使用现有契约；新运行状态的类型统一放入 `src/jobagent/schemas/`。

每个运行拥有独立 `run_id` 和工作目录。每个步骤记录输入摘要、输出契约、产物引用和完成状态。两个相同 prompt 类型不能共用请求文件。状态写入采用原子更新，并拒绝两个宿主同时持有同一运行的执行权。

恢复首先核对产物摘要和版本。已完成的确定性步骤可复用；外部发送结果不明时交给人核实，不能通过再次发送推测结果。Codex 与 Claude Code 使用同一工作区时可以交接，但不同宿主不共享或复制凭证。

## 上下文与定向生成

- 职业事实：CandidateProfile 与 EvidenceItem，只有已确认的证据能支撑最终简历。
- 用户偏好：目标岗位、地域、薪酬及用户拒绝某岗位的原因；可修改，不自动提升为职业事实。
- 任务状态：当前阶段、等待事项、输入版本与产物路径；不依赖聊天历史完成恢复。
- 操作策略：按当前步骤加载 references。L0 索引用于发现，不能把未实现 adapter 当作可执行工具。
- 改写请求只携带当前 JD 需求、相关证据和目标简历条目，记录选取理由与遗漏项。第一阶段采用可解释的确定性筛选，不依赖向量数据库。
- 生成结果必须建立非空、覆盖全部实质性简历条目的主张台账。校验条目与主张的双向关联；数值独立核对，语义蕴含由独立复核步骤判断，不能仅采信生成步骤的自评标签。
- 保全完整 JD、证据版本、策略与视角摘要。补充上下文不得编造缺失事实。

## PDF 与投递体验

PDF 默认继续通过既有 resume-builder 渲染边界完成。首次运行探测它及编译依赖，并提供明确安装路径。宿主存在合规可用的替代渲染工具时，可以通过已声明的适配边界使用；无法渲染时停在已验证的简历内容阶段，不声称 PDF 已生成。

交付 PDF 前检查文本可抽取性、阅读顺序、页数和内容一致性。评审包同时展示目标岗位、定向内容差异、缺口、PDF 与拟发送消息。

每份申请独立审批，审批绑定当前岗位、简历、消息与策略摘要。截图中的多份任务体验以逐份处理和汇总表现；不新增 `BatchApplication` 编排，也不让一个宽泛的确认授权多份投递。

当前猎聘连接器只传岗位 ID 与类型，未传定制附件和消息。发布前必须明确解决实际交付内容与审批对象的一致性：平台支持经过审核的附件传输时接入；不支持时停在人工上传及提交，不把职位 apply 调用记为定制简历已送达。

招聘方预先沟通是独立外部发送。只有用户明确要求并确认具体收件方和消息后才发送；缺少受支持的消息连接器时提供草稿与人工交接。

## 宿主适配与定时工作

两种宿主共享领域状态；薄适配负责能力清单、用户提问、人工接管、调度注册和结果展示。适配不得提供关闭审批、忽略证据或绕过平台门控的选项。

定时发现岗位由宿主提供调度。只有用户明确请求后才建立计划，并保存时间、时区、候选人工作区和只读发现范围。每次运行检查候选人就绪度；通知仅在有新的可评审岗位、失败或需用户处理时出现。定时任务不自动批准或投递。

Codex 的不同界面、Claude Code CLI、Desktop 和 cloud 的调度能力分别探测。仅有当前会话循环时，如实说明退出后停止；需要本地候选人数据或已登录浏览器的任务不能默认迁移到无法访问这些资源的云运行环境。第一阶段不自行安装操作系统后台服务。

浏览器、会话接管、安全凭证输入及通知使用实际存在的宿主能力。缺少安全凭证界面时，用户直接在网站登录；skill 不要求用户把密码或验证码发进聊天。平台登录、验证码、风控及限流均暂停等待人处理，随后显式恢复。

## 第一阶段与验收

第一阶段交付可分发 skill、匹配版本 runtime 的初始化、Codex/Claude Code 接入说明、隔离的运行状态、恢复入口、可信简历生成与 PDF 交接、逐份审批和准确结果汇总。调度和浏览器能力以探测后接入或明确降级为准。

现有硬边界保持：领域模块不依赖宿主 SDK 或浏览器；确认事实只经 CandidateEvidenceService.confirm；无批量投递编排；无绕过平台验证；私密数据不进入分发包或 Git。新增命令同步能力目录；更新入口文档的过期阶段说明。

验收使用合成数据与 mock 连接器，包含：

1. 从干净临时目录安装；不依赖仓库 cwd 或开发者全局设置。
2. 两种宿主的加载结构与状态协议兼容；真实宿主验证需具备相应工具和账号，未实测部分明确标记。
3. 完成证据确认、JD 定向生成、PDF 检查与单份审批流程；任何空台账或未覆盖条目被拒绝。
4. 中断、重启和跨宿主交接后保留已验证产物；并发 run 不覆盖文件。
5. 岗位选择不授予发送权限；产物修改使已有审批失效。
6. 未支持的平台、渲染器、浏览器或调度器返回明确人工交接，不能报告虚构成功。
7. 投递结果不明时不重发；成功与失败汇总都能追溯实际产物和尝试记录。
8. 运行 CONTRIBUTING.md 中的四条质量门禁；发布构建验证依赖版本和资源摘要。
