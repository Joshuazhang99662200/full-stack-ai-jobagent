截至本轮开始，Gemini 已在 BOSS 真实页面完成 20 条已加载会话摘要和 10 条搜索职位列表读取；这不等于完整 JD、查重、审批或发送已完成。猎聘既有一条完整 JD 入库已验证。飞书机器人认证及既有监听进程可用性将分别复核。审批触发自动唤醒 Codex 的常驻调度仍不可假定存在。

## 总体定位

本人在后续联调中明确：Codex 给出搜索策略，Gemini 通过猎聘 MCP 获取职位列表，并自主读取完整 `jd_raw` 回传；Codex 根据真实 JD、候选人已确认证据和现有写作规则生成招呼语，通过现有飞书接口提交本人审批。审批登记成功后，准确任务同步 Gemini，由其执行并回传真实结果。

Codex 不操作浏览器、不读取采集截图，也不编写或调试 Gemini 的浏览器实现。浏览器、详情读取、截图解析和聊天交互完全由 Gemini 自主负责。JobAgent 继续负责契约、业务规则、审批记录、执行授权和审计；常驻调度器只承担确定性派发，不获得审批权。完整 JD 的唯一契约字段为 `jd_raw`，不另造 `jobraw`。

审批入口沿用现有飞书卡片：本人勾选、可编辑准确正文并提交，处理器校验和登记后回填卡片。后续执行任务从已持久化的有效审批记录产生，不另要求本人回本聊天重复确认同一内容。涉及简历成品的逐份审批仍按对应业务规则处理。

## 聊天型来源流转（BOSS／智联）

1. **策略与交接**：Codex 根据本人搜索条件生成 fetch 策略，经业务层校验形成任务，写入 `tasks_to_gemini`。通信适配器发送任务，Webhook 携带关联编号与事件引用；Codex 不操作浏览器。
2. **采集与入库**：Gemini 领取任务，自主使用已获准的浏览器或来源工具读取 JD，通过既有 `worker ingest` 提交结构化数据。JobAgent 校验完整性、来源与幂等后原子入库；Gemini 回传完整字段和实际入库回执至 `results_to_codex`。
3. **判断与起草**：Codex 接收完整结构化 JD 和入库回执，核对候选人已确认证据、匹配与查重后按现有规则起草准确招呼语。缺完整 JD 时不使用列表摘要拼出正文，也不为联调编造内容。
4. **飞书同步与审批**：Codex 通过既有 `outreach ask` 和飞书通知接口推送待批全文及 JD 核心依据。现有审批处理器接收本人决定、登记审批并回填状态；未通过项目保留原因。Gemini 不代替本人点击批准或生成审批记录。
5. **准备执行**：可靠事件层发现新的有效审批，按获批条目产生待执行任务及 `greeting.ready`。队列中保存审批和批次引用、内容摘要及目标，不把通知成功当成执行授权。
6. **临近动作复核**：Gemini 准备发送时，经本地接口调用既有 `worker claim-greeting`；核对正确目标、页面和历史记录后，在真正点击前请求 `worker authorize-greeting`。本地复查摘要、审批时效、站点租约与节奏后给出一次性授权。
7. **回读与记账**：Gemini 使用获批原文执行一次，返回准确 URL、可观察正文、实际状态和异常原因。既有 `worker record-greeting` 校验并提交审计、回执、完成事件。无法确认就记录 unknown/intervention，不自动再次发送。
8. **展示与回传**：Gemini 通过通信适配器回传实际结果，Codex／既有通知适配器同步飞书状态；同一通知幂等，不由双方重复发送。执行记账无需再次调用模型来判定“是否成功”。

这些事件名为目标协议建议，当前没有对应的完整派发实现。

## 两条队列与业务表

首版使用一个本地私有数据库，保留两条逻辑队列。本机 AGY／Gemini 通过类型化业务接口提交写入，由 JobAgent 落库，不用临时 SQL 修改业务表。

| 数据组 | 保存内容 | 写入责任 |
|---|---|---|
| `tasks_to_gemini` | fetch / approved_greeting 任务、业务引用、输入摘要、领取者、状态、租约 | 本地受控服务；搜索单来自 Codex 策略，执行单来自已登记审批 |
| `results_to_codex` | 完整岗位观察、采集错误、Gemini 回读、飞书同步回执与结果摘要 | Gemini 提交结构化载荷，本地适配器验证后写入；平台回读交既有 Worker 校验 |
| 现有业务表 | 正式职位、证据、匹配、外联批次、原问题、审批、审计、Worker 回执 | 现有 JobAgent 服务 |
| `event_outbox` / 消费记录 | event_id、关联任务、类型、版本、摘要、派发状态、处理确认 | 业务提交与事件创建在同事务；消费者按 event_id 幂等确认 |

结果队列表示结果等待验证/处理，正式业务记录表示已经过领域门禁。拒绝结果保留原因；不能把写入暂存区视为入库或发送成功。队列完成标记引用正式业务回执，避免两套互相矛盾的成功状态。

完整岗位对象与原始观察均保留，包括 null、JD 原文、招聘方、来源 URL、采集时间和检索词。Webhook 携带事件引用、版本与摘要即可；接收方通过受控接口读取完整载荷。长载荷使用有数量、长度及摘要校验的分块或完整产物；缺失与截断必须拒绝验收。

## 事件与通知的责任

- 数据库不会自行启动 Agent；常驻调度器读取已提交的 outbox 并通知消费者。
- 本机组件之间可使用进程通道或本地 HTTP；将来接远程节点再增加已认证 HTTPS webhook。
- Gemini 端通过本机 AGY CLI 收发任务和结果。应显式绑定实际可用的 Gemini 模型和会话，验证连续任务的关联；不向现有终端盲目注入键盘输入，不把 CLI 启动视为任务完成。
- Codex 端承担搜索策略、JD 文字判断、招呼起草、飞书待批内容推送和审批结果交接；浏览器能力留在 Gemini 端。Webhook 接收服务与通信适配器只负责传输，收到事件不代表当前聊天已自动唤醒。
- 飞书发卡由 Codex 通过既有接口执行，状态回填与审批登记沿用现有处理器；审批后的内容交 Gemini，避免双方重复发卡或重复发送招呼。
- 通知允许幂等重投，消费允许幂等确认；不确定的实际外发动作先对账，不由通用重试器重做。
- 调度器限制并发、按站点串行派发，并遵守现有叫停、租约和节奏；审批没有扩大原先允许的工具或站点范围。
- 当前寻源包含猎聘、智联和 BOSS，按上表分流。BOSS 曾有真实访问限制，历史证据保留；本人明确恢复测试且正常页面读取已证实，不再以无条件旧停用记录阻断新任务。任何来源出现当前真实验证码、风控、限流或访问限制仍立即停站。通信层不新增网页定时巡检，Codex 不操作浏览器或读取采集截图。

## 飞书已有链路的准确接点

既有源码接点如下，由 Codex 推送待批内容，处理器登记本人决定，Gemini 消费获批执行任务：

- `src/jobagent/cli/notify.py` 暴露通知与 `feishu-listen`，监听器通过 CLI 的事件消费输出处理卡片。
- `src/jobagent/bridge/feishu_approval.py::handle_card_event` 验证本人、已登记卡片和未关闭状态，调用领域审批服务并保存审批。
- 本人改写的勾选条目会形成新批次和相应审批；一个提交可能同时批准原批次与改写批次。下游应从持久化审批逐项派生任务，不能只读单个 `CardOutcome.approval_id`，也不能继续用旧原文。
- `outcome_card` 回填的是审批处理结果；实际执行由独立 Worker 执行并回读。

新增的工作是把每一份成功登记的审批可靠地连接到执行队列。目标是在审批写入的同一事务产生 outbox 事件，并用审批与条目编号的唯一键防止重复派发；对启用事件层前已存在的审批，通过对账补建一次，重新检查时效与撤回状态。当前审批写入与旁边的卡片登记文件并非统一事务，这项可靠性需实现和故障测试，不能用监听器的一行输出替代持久事实。

审批监听器按指定小时数结束，目标运行架构需由监督进程明确启动、记录健康状态并在允许的生命周期内恢复。这里只定义职责，没有启动或改动现有飞书监听器。

## 新增范围与验收

新增范围收敛为任务与事件持久层、常驻调度器和 AGY／Gemini 通信适配。Codex 承接策略、文字结果加工和飞书推送，Gemini 承接浏览器执行。保留现有业务服务、字段契约和飞书审批语义，不恢复旧浏览器执行层。

顺序为：有效 Gemini 模型的合成回声 → 同一通信会话的任务关联 → Gemini 猎聘 MCP 搜索和自主详情读取 → 完整 JD 入库与回传 → Codex 起草并推送飞书 → 本人审批登记 → 单条获批任务同步 Gemini 执行与实际回读。

一键投递单独验收：先核实 MCP 当前实际暴露的工具、参数、简历版本和回执能力。只有 `jobId`／`jobKind` 的接口不能声称已交付指定附件或准确消息，也不能借招呼语审批直接投递简历。当前领域投递连接器仍保留不能交付获批附件与消息时的人工交接边界；聊天可由 Gemini 在正常授权的浏览器中完成。

每阶段分别保留验收证据。真实账号、浏览器执行和飞书端到端接通不能由模拟测试或代码存在推断；本次仅完成架构梳理与源码映射。
