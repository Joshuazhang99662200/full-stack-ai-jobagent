# 给 Muse：二级页恢复逐项展示，招呼语用两种状态区分

本轮在 Muse 宿主层修改，不改仓库前端代码。沿用已经恢复的白、灰、浅蓝设计语言。

一级页面按 [五列方案的排序与整行点击要求](muse-five-column-progress-2026-11-01.md#一级页面左上角增加排序切换) 执行：左上角提供“按匹配度 / 按入库时间”，默认匹配度降序，入库时间按新到旧；点击整行任意普通区域可打开本岗详情。二级页右上角按钮文字始终保留“关闭”。

这次截图把信息删减、合并得过头了：公司、渠道、地点、薪资串成一行，关键要求藏在链接后面，进展又成了一段话。需要恢复一项一项的阅读顺序，不能把“简洁”做成“所有东西挤在一起”。

## 一、二级页按条目组织，不恢复满屏大卡片

| 顺序 | 内容 | 默认怎么显示 |
|---|---|---|
| 1 | 岗位名称 | 顶部清楚显示，关闭按钮在右上角。 |
| 2 | 公司、渠道、地点、薪资、原岗位链接 | 分成可辨认的独立条目。宽屏可以两列对齐，窄屏逐项换行；不要再用一串分隔符连成一段。 |
| 3 | 职位要求 | 直接列关键职责与要求，一条一行；完整 JD 另有展开入口。不能只有“查看职位要求”链接而看不到任何要点。 |
| 4 | 关键词 | 在职位要求下方放少量核心词，轻量标签即可，不再单独套卡片。 |
| 5 | 进展与本人待办 | 进展单独一条，由 LLM 写清当前事实。确有本人待办时另起一条展示具体问题或动作，不能混进岗位信息或招呼语正文。 |
| 6 | 招呼语 | 用下文的“拟发送 / 实际发送”状态与样式展示。 |
| 7 | 简历及相关材料 | 有当前实际材料时独立列出，能打开成品。影响当前决定的缺口也就近说明。 |
| 8 | 历史与沟通 | 保留清楚入口，展开后逐项看旧稿、已发材料、消息和本人决定；不把全部类别压成一段摘要。 |
| 9 | 工作流程及岗位操作 | 底部按独立节点显示流程；“放弃岗位”外显为红色按钮，不藏在“更多”中，不显示“先放一放”。 |

每个条目之间靠间距、对齐和必要的浅分隔线区分。不要求每项加边框，也不把所有条目套在一个大文本框里。保持正常字号和行距，弹窗宽度随宿主可用空间调整，不靠缩小文字凑进小盒子。

标题只保留有助于辨认的。“公司”“地点”“薪资”等字段标签可以保留，它们帮助用户快速找到信息；重复的说明性副标题继续删除。缺失非必要字段不逐项堆“未记录”，但影响当前判断的未知不能省略或补猜。

## 二、招呼语只有两种展示状态

统一用“招呼语”作为内容名称，用一个简短状态标记区分：**拟发送**、**实际发送**。不要再靠“准备发送的招呼语”“实际发出的招呼语”“这份是已发文本”等多种标题和解释段落表达区别。

| 展示状态 | 正文样式 | 交互 |
|---|---|---|
| 拟发送 | 正常深色字体，放在文本框内。浅边框、白底，获得焦点时用蓝色提示。 | 当前审核或编辑任务允许修改时可编辑；尚未接通修改能力则只读，但不伪装可保存。展示准确全文，保存修改保留新旧版本。 |
| 实际发送 | **灰色、斜体、无框**。直接排在页面上，背景透明，无输入框边界、无灰底卡片、无引用竖线。 | 只读，可选中复制。不能在这段已发正文上直接修改历史。 |

“无框”包括正文外面也不再套一层浅色边框。不能用禁用的 textarea 模拟已发送状态。灰色采用可读的次要文字色，例如现有的 `#647184`；不降低到难以辨认的透明度，也不缩小字号。斜体是辅助区分，保留可读的状态标记，不能仅靠颜色辨认。

有可靠发送时间时，可在“实际发送”旁放简短时间；没有时间不推算。正文必须是当时真正发出的全文，不从当前草稿替换，也不让 LLM 润色已发记录。

### 当前截图应该怎样改

截图中已有“实际发出的招呼语”的白色边框块，应改成：

- 内容名称仍为“招呼语”，旁边标“实际发送”。
- 下方已发原文改成灰色斜体，直接呈现在白色页面上，去掉正文框及外层边框。
- 移除正文里重复解释“这段招呼已经发出去”的文字；整体业务进展仍可简短说明目前等待什么。
- 不显示针对这段已发文本的接受、批准或保存修改按钮。

只有拟发送的内容才保留文本框。需要准备后续回复或新版本时，另建对应草稿，不能把已发原文改回可编辑框。

## 三、草稿和已发内容同时存在时都要能看

“两种状态”不意味着只保留其中一份，或用一个开关切换后覆盖原文：

- 当前有待本人审阅的拟发送内容，先展示文本框，相关已发内容在下方独立展示或从历史展开。
- 当前没有新稿、只有实际已发内容，就直接展示灰色斜体原文，不再加一个空文本框。
- 有多次发送或多个历史版本，按对应联系轮次与真实记录逐条查看，不拼接成一份正文。
- 发送结果还不明时，宿主先核实，不强行套“实际发送”样式。必要时在进展中说明“发送结果还没确认”，不另造一个已发事实。
- 拟发送不等于已获批准，文案被接受也不等于实际发出。这些继续由现有业务记录与门禁判断，不以文本框样式决定业务状态。

## 四、审核界面继续保留上下文

招呼语审核仍按 **JD 要点 → 关键词 → 拟发送文本框 → 适用审核操作** 排列。不能为了压缩页面把上方要求都折叠掉，让本人脱离岗位要求审文案。

JD 要点和关键词来自本岗实际职位说明，允许 LLM 自由提炼；不补造未读取的要求。仅有部分职位说明时，简短说明内容不完整，并保持相关步骤的既有门禁。

普通详情不常驻全部审核按钮；从红点进入则直达审核内容。按钮不附成排机制说明，只有影响这次操作的问题就近说明。猎聘等不适用招呼的渠道不硬塞这块，仍展示适用材料。

## 五、底部流程恢复本地组件的节点模式

参照本仓库 [JobWorkflow.tsx](../frontend/src/JobWorkflow.tsx)：每一步是独立的小节点，带阶段名称、完成标记或必要的状态。不要继续使用截图中“一串小圆点 + 四个词 + 箭头”的纯文字流程，也不要把全部阶段合并成“发送并核对结果”。

参考阶段顺序为：获取信息、查看详情、评估匹配度、写招呼语、检查材料、准备审批、核对结果、整理结果。根据实际渠道省略不适用步骤，例如猎聘不显示写招呼语。它是已记录工作的展示，不是强制每个岗位走完所有步骤。

- 已完成的节点：浅蓝底、蓝色文字或完成勾。
- 未开始或没有记录的节点：浅灰底、灰色文字；有必要时区分“未开始”和“未记录”，不将未知当作尚未开始。
- 正在执行或等待处理的节点：清楚描边，并标“现在”。允许多个并行节点，不强行只选一个。
- 心跳失效、失败和岗位已结束：按真实记录显示，不继续标成正在做，也不因后续节点完成就把前面全部点亮。

节点有正常间距，窗口变窄时换行，保持名称能看清；不能缩成一条难点选的小字链，也不放大为整屏大卡片。可打开相应工作记录，但点击节点不构成批准或执行。

只恢复节点的视觉和记录逻辑，不复制组件里反复出现的进展段落、长图例或规则说明。准备审批完成仍不等于本人已批准，相关业务校验保留在内部。

## 六、岗位操作直接外显，删除重复入口

普通详情不再设置一个“更多”折叠区来藏岗位操作。将 **“放弃岗位”** 直接显示在弹窗下方，使用明确的红色按钮，和流程区适当分隔；不要恢复绿色主按钮，也不用一大段小字解释它。

点击后调用既有的岗位放弃服务，保存本人本次决定、岗位及联系轮次；业务结果确认成功后再更新界面、红点与排序。保存失败明确反馈，不能仅隐藏卡片冒充放弃。历史材料、消息和已发事实继续保留，不删除旧记录。服务未接通时禁用并说明，不造假按钮；不再额外套“更多”或无实际必要的重复确认层。

**删除“先放一放”按钮。** 用户这次不想处理，点右上角 **“关闭”** 按钮 关闭即可；关闭只结束查看，不记录暂缓、不放弃岗位、不消除本人待办、不触发发送。原来已经存在的真实暂缓决定仍保留历史，不因删掉按钮而改写。

如果已经编辑了招呼语或意见，关闭时仍须妥善保存输入，或只在确有未保存改动时处理草稿去向，不能把关闭误记成一次业务决定。

招呼语接受、修改与批准等操作继续只在对应审核视图显示。把“放弃岗位”外显，不表示在普通详情重新铺回全部审核按钮。

## 七、这轮改完怎样检查

1. 不读整段话，也能分别找到公司、渠道、地点、薪资、JD 要点、进展和招呼语。
2. 职位要求和关键词直接可见，重要信息不全部藏在链接后面。
3. 拟发送内容是正常字体的文本框；实际发送内容是灰色斜体、无框正文。两者没有靠长段解释才能看懂。
4. 实际已发文本不可编辑，能复制；草稿修改不覆盖历史，样式不会改变业务状态。
5. 历史材料、简历和沟通依然能逐条查看；没有恢复空记录堆叠、长篇内部解释或绿色版本。
6. 底部是可辨认的独立流程节点，蓝色完成、灰色未开始或未记录、当前标“现在”；没有退回纯文字小圆点链。
7. “放弃岗位”红色按钮直接可见，没有“更多”折叠和“先放一放”按钮。点“关闭”仅关闭，放弃只有业务保存成功才生效。
