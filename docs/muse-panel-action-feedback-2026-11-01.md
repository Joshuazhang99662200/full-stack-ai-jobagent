# 给 Muse：红点要能办事，点开就知道该做什么

请先在 Muse 宿主层修改现有交互面板。本次不修改仓库前端代码，也不要求重做整套页面。保留已有岗位、材料和历史记录，优先修正“哪里要我点、点开让我干什么、点完发生什么”这三个问题。

岗位操作以最新 [二级页节点与按钮要求](muse-detail-items-and-greeting-states-2026-11-01.md) 为准：删除“先放一放”按钮，右上角“关闭”按钮 仅关闭查看；“放弃岗位”直接外显为红色按钮。

## 当前页面哪里让人难用

- 一排“需要你”没有说清具体要决定什么，用户只能逐个试点。
- 点开后首先看到运行信息、技术字段和长段解释，真正待决定的问题没有操作入口。
- “判断基本要求中待核对的条件”把判断工作交给用户，却没有指出哪条要求、哪里冲突、有哪些选择。
- “已保存的工作……是否已联系……没有足够记录”在各行重复，重要进展反而看不见。
- 匹配分数很高，同时又显示“待核对”，没有解释评估和硬条件的区别，让用户不知道该信哪个。

不要只把技术词换成中文，再把同一批技术说明放回主页面。把真正需要用户决定的事放在最前面。

## 页面上的话直接按下面改

下面是给用户看的文案。Muse 应按真实情况选用，不要把整张对照表、使用条件或实现说明搬进页面。

这些说法是示例，不是固定模板或可选句子的白名单。主表进展按 [五列布局与 LLM 进展说明](muse-five-column-progress-2026-11-01.md) 由 Muse 根据事实自由组织语言。

“还没有回复”“等你审阅”等结论，必须先核对对应记录。无法确认时用相应的未知提示，不能为了让话顺一点就补出进展。“记下了”之后，应紧接实际保存的决定及后续安排，不让用户猜刚才点了什么。

## 用户页面不放这些内容

从列表、普通详情、工作记录正文、待办弹窗和流程说明中移除：

- SQL 查询、取数公式、加权公式、原始计算过程。
- 数据库表名、字段名、JSON 键、内部状态码。
- 队列路径、内部记录编号、摘要哈希和模板版本串。
- 重复的“无执行者”“无恢复点”“没有开始时间”等非必要空值说明。
- 长段的审批边界、数据模型和实现原理说明。

这些内容留在宿主内部的排查记录中，不作为普通用户的默认页签或工作进展正文。确需核对原始字段时，由用户主动进入“更多 → 排查问题”查看；保留可追溯记录，不删除原数据。一般用户不需要先读技术资料，才能理解进展或作决定。

用户真正需要核对的是：岗位要求原文、自己的相关经历、招呼语全文、简历成品、对方消息，以及自己作过的决定。这些不能随着技术信息一起藏起来。简历的可读版本名和实际文件名可以保留，点击后要能打开文件；它们与内部模板版本串、存储路径有区别。

这里移除的是系统内部实现说明。岗位要求、简历或对话原文里本来就有的专业内容照常保留，不改写原文。

匹配结论写成具体理由，例如在证据支持时写“你的项目经历与岗位要求比较接近，但办公地点还没核实”。分数如保留，放在次要位置，并用普通语言说明它代表什么；不要展示取数公式，也不要用“匹配 100”替代判断理由。

## 先改列表：需要我处理，就给红点

用小红点替换重复的黄色“需要你”色块。红点表示**这个岗位有尚未处理的本人决定**，不是“没读过”，也不泛指系统有异常。

- 红点旁写短而具体的动作，例如“看看工作地点”“看看招呼语”“回复对方的问题”。不要仍然只写“需要你”。
- 点击红点或旁边的动作文字，都直接打开对应待办。整个入口要容易点击，不能要求用户准确戳中一个小圆点；键盘和屏幕阅读器也须能识别“哪个岗位、需要处理什么”。手机上不能只靠悬停提示解释。
- 没有本人待办，就不显示红点；已有待办但暂时无法核对时说明状态未确认，不擅自清除。
- 顶部例如写“还有 3 个岗位等你看看”，数字换成真实数量，与红点岗位数一致。同岗有多个待办时只计一个岗位，展开后再说明有几件事；不能混用岗位数和事项数。
- 点开、读过或关闭弹窗都不清除红点。只有对应事项真正处理并保存成功，才更新红点；同岗还有其他待办时继续保留。
- 系统故障用错误图标和具体说明表达，不复用红点假装需要本人作业务决定。保留原有白、灰、蓝配色，红点只作少量提醒，已完成 workflow 节点仍用蓝色。

列表每行优先只说三件事：**岗位是什么、目前到哪一步、有没有事需要本人决定**。例如有证据时写“招呼语写好了，还没有发送。”；只有评估记录时写“已经评估过这个岗位，后续进展还没查清。”。同一条进展说一次，不再分别在摘要、标签和流程上方重复整段文字。具体情况直接按 [列表进展文案表](muse-job-detail-dialog-2026-11-01.md#列表中间的进展栏也一起改) 选用，并核对右侧待办和弹窗内容一致。

## 再改点开后的内容：先给问题和选择

点击待办后，弹窗顶部直接呈现以下内容，不先跳到工作日志，也不要求用户再翻多个页签寻找入口：

| 用户应该立即看见什么 | 如何写 |
|---|---|
| 要我决定什么 | 一句具体问题，例如“这个岗位需要异地线下办公，你愿意继续了解吗？” |
| 为什么问我 | 展示岗位要求、本人已确认的相关条件以及需要取舍的地方。引用简短原文，可继续查看完整来源。 |
| 有哪些选择 | 用明确动词命名按钮，避免只有“确定 / 取消 / Accept”。 |
| 每个选择会发生什么 | 在选项旁简短说明：仅记录偏好、继续准备材料、暂不推进，还是另有实际外部动作。 |
| 处理后是什么结果 | 显示已保存的决定、岗位接下来怎么处理，以及是否仍有其他待办。 |

以下只是交互示例，不能写成真实岗位事实或用户的通用偏好：

> **这个岗位在外地，你愿意继续了解吗？**
>
> 招聘信息写明需要到办公室工作，暂时没有说明能否远程。
>
> **继续了解**：先保留这个机会，继续准备材料。
>
> **帮我拟一段询问**：先写好询问办公方式的消息，给你看过再决定是否发送。
>
> 这一步只记录你的选择，不会发消息或投递简历。

该示例里的办公要求也是假设，不能直接套到真实岗位上。若选“继续了解”并保存成功，可以显示“记下了，继续了解这个岗位。”。不想处理时关闭即可。后续工作是否开始、是否完成，按实际执行情况另行更新。

只有对应服务已接通的选项才能执行。未接通时显示“这里还不能保存选择，请在对话里告诉我”，并确保对话确实可用；不能做一个只改变卡片颜色的假按钮。没有决定时可以关闭弹窗，保留待办，不强迫用户二选一。

同岗多个问题时，先展示当前问题，并允许查看其他事项。处理完一项后提示“这件事记下了，还有一件需要你看看”，数量按实际情况写，不要突然跳到别的岗位。用户从岗位名称进入普通详情时，也应在顶部看到待办入口；材料和历史页签继续保留。

## 哪些事不应该扔给用户

在显示红点前，宿主先做判断：这件事是否真的需要本人决定，还是 Agent 还没有把记录读完？

| 情况 | 宿主应先做什么 |
|---|---|
| 只知道状态叫 REVIEW，却说不清哪条条件待核对 | 找出具体岗位要求、现有证据和不确定点；不能把状态名直接变成用户待办。 |
| 缺工作地点、办公方式或 JD 详情 | 在授权和现有预算内核对来源；受限时报告缺什么、为何查不到。只有确实需要本人提供信息或选择人工协助时，才列成具体待办。 |
| 本人已有明确适用规则 | 复用规则处理；不每个岗位重问一次，也不借此重开首次配置表单。必须由本人取舍的例外才提出具体问题。 |
| 没有近期执行记录、没有保存下一步 | Agent 核对自己的执行和计划。不能仅因这些字段为空，批量标“需要你”。无法继续时说明真实阻塞及所需帮助。 |
| 匹配评估较好，但有必要条件未核对 | 说明哪段经历比较符合、哪项条件还不知道。分数不能代替解释，计算公式不进用户页面；不能把分数包装成“百分百适合”。 |
| 有草稿、有文案接受记录 | 展示准确全文及决定含义。文案接受、逐项发送批准与实际发送分别核对，不能互相替代。 |

## 点完以后要有反馈，旧内容不能丢

用户提交决定时显示“正在保存”，防止重复提交；保存失败就说明失败并保留待办。只有真实业务服务保存成功、重新读取确认后，才显示“已保存”并更新列表。材料或版本已变化时，保留待办并说明需要重新核对；结果未知时先核验，不能提示用户反复点击重试。

继续了解、暂缓、放弃、批准和发送是不同决定。按钮名称和结果必须一致，不能点“暂不推进”就永久关闭，不能点“继续”就发送招呼语或简历。涉及外部发送时，仍须展示具体岗位、准确全文和实际附件，经过已有逐项审批与发送前校验，执行后核实结果。

弹窗下方保留工作流程；旧招呼语全文、旧简历、拟投递安排、批准记录、实际发送内容和双方沟通原文继续能打开查看。它们是用户作决定的依据，不能为了精简页面被删掉或只留下技术字段。历史恢复要求沿用 [文字与历史记录修订清单](muse-panel-correction-2026-11-01.md)。

用户页面不放字段名、SQL、取数公式和内部排查说明。需要说明问题时，只写它对这一步有什么影响，例如“之前的简历暂时打不开，暂时不能核对附件”，不要让用户自己从错误码推断。

## 请按这个顺序改，并在 Muse 中验收

1. 先核对现有“需要你”事项，区分本人决定与宿主待核查问题，删除错误分类，保留核对依据，不删除真实未办事项。
2. 将真实本人待办改为“红点 + 具体动作”，点开直达问题、依据和选择。
3. 接通决定保存、失败反馈和重新读取，再更新红点及统计。
4. 收起技术说明和重复兜底话，核对旧材料与历史入口没有丢。

验收时至少逐项演示：

- 看一行就能说清当前进展；看到红点就知道要本人处理什么。
- 点击红点直接看到具体问题和可用选项，不必读 JSON 或寻找下一步。
- 关闭弹窗后待办还在；保存失败不消点；一岗多项只办完一项时红点仍在。
- 成功保存后，关闭再打开、刷新或恢复会话，已保存决定仍一致，不重复询问。
- 没有个人待办的岗位不乱标红点；Agent 缺记录不冒充用户欠处理。
- 能查看旧招呼语、打开简历并核对已发内容；普通“继续”不会触发招聘发送。

交付时说明哪些交互已实际验证、哪些服务还没接通。不用静态截图或改过的文案代替可操作面板的验收，也不要为了验收试发招聘消息。
