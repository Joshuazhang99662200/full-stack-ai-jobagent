# 给 Muse：岗位面板的文字与历史记录修订要求

本次修订针对 Muse 宿主中的执行和展示。请在自己的私有工作区核对数据、修订交互面板，不要求修改本仓库前端代码。仓库组件用于参考；直接照搬组件、字段名或调试说明，不代表宿主面板已经交付。

待办红点、点开后的问题与选项、提交反馈和消点规则，继续按 [红点与待办交互修订要求](muse-panel-action-feedback-2026-11-01.md) 执行。

用户反馈：页面读起来困难；以前准备的招呼语、简历、拟投递安排、实际发送内容及沟通记录必须保留并能查看。当前截图可确认部分正文被“见队列”替代，技术来源被放在“执行者”中；其他材料是否已在别的页签或数据源保存，需要逐项核对。截图无法证明源文件丢失，也无法证明材料、审批或发送已经完成。

## 一、先把话说清楚

日常界面写给求职者看。每段内容应说清：做了什么、产出了什么、现在卡在哪里、下一步做什么、需要本人决定什么。字段名、SQL、取数公式、内部状态码和技术校验说明不进入普通页面；留在宿主内部排查记录，需要时再由用户主动查看。页面可直接采用的文案见 [用户文案对照表](muse-panel-action-feedback-2026-11-01.md#页面上的话直接按下面改)。

| 现在的问题 | 应改成的表达和行为 |
|---|---|
| “未记录；已写招呼语、准备审批、检查材料、评估匹配度” | 按事实写：“招呼语写好了，材料也检查过了。”是否联系过还不知道时，另写“有没有联系过招聘方，还需要核实。”不要把两种结论挤成一句。 |
| “招呼稿版本=……；稿件全文见队列，不在此重复全文” | 写“招呼语写好了，请你看看。”直接展开准确全文，提供“以前的版本”入口，不能要求本人去翻队列文件。 |
| “卡片决定=accept；决定已记录……” | 若核对后只代表接受文案，写“你选好了这版文案。”未批准发送的事实也已核实时，再写“还没有批准发送。”不把接受文案写成发送批准。 |
| “执行者：queue.jsonl:……” | 文件路径和字段名不进入日常界面。确有必要时显示真实执行者；没有记录就不在普通页面占一栏。 |
| “开始未记录”“恢复点未记录”挤在每项工作标题中 | 主标题写“招呼语已写好”“材料已检查”。确实需要查看时，在记录详情中说明“没有保存开始时间”或“没有保存继续处理的位置”。 |
| “当前没有进行中的工作” | 已确认停止时可用；仅缺少执行更新时写“最近有没有继续处理，还需要核实。” |
| “下一步尚未安排”“暂时不需要你处理” | 先查已有安排和待办。确实无安排写“还没安排下一步。”待办尚未查全写“还有没有需要你处理的事，暂时不能确定。” |
| “Signal / Harness”作为普通用户页签 | 可显示“反馈与改进 / 执行记录”，技术名称留在数据来源。分别说明收到什么反馈、是否已采用、关联哪次工作；未接入时直接说明。 |

上表中的表达是有条件的范例。按查到的事实选用，不能把示例状态批量写进真实岗位。时间缺失写“时间未保存”；不要把版本标签、文件修改时间或本次导入时间当成过去的起草、批准或发送时间。

## 二、岗位详情应改成什么

保留一岗一行的主视图，详情继续使用弹窗。进入任意岗位后，本人应能看到以下内容：

1. **现在进展**：最后确认的业务进展、已做的工作、正在做的工作、下一步安排和需要本人处理的事项。每条结论都能找到对应记录。
2. **招呼与简历**：当前草稿全文、以前写过的版本、准确获批版本、简历成品与历史版本。点击即可在私有环境中查看，附件可实际打开；文件路径本身不算可查看的简历。
3. **投递安排与结果**：把“拟投递”“等待本人批准”“已批准待执行”“已尝试但结果不明”“已核实发送”分别说清。不存在的状态不补造；不能用一句“已完成”合并这些含义。
4. **沟通记录**：双方说过什么、谁发的、何时发生、来源在哪里，以及需要跟进什么。允许查看原文，摘要只帮助阅读。
5. **工作记录与流程**：保留原有的起草、修改、复核、本人决定、执行和核验记录，能打开相关产物。弹窗底部保留 workflow；有完成证据的节点蓝色，未开始或未记录灰色，当前步骤标“现在”。历史缺失、并行和反复修改不能被一条理想流程覆盖。
6. **需要时再看排查资料**：完整字段、来源与关联继续保存；用户主动进入“更多 → 排查问题”时才展示，不作为默认页签。招呼语、简历和消息原文仍在各自页面直接可看，不能藏进排查资料。

原有内容不得因新增 workflow、换弹窗或简化界面而消失。按内容分组和折叠即可，不要求把所有历史全文同时铺满屏幕；每个保存过的版本必须在当前岗位详情里有明确入口。

渠道继续分别处理：BOSS、智联按可用能力展示招呼与材料；猎聘不生成不适用的招呼步骤或按钮。若历史源里已有相关文本，保留原始事实供核对，不能据此声称该渠道支持发送。

## 三、逐项把遗漏的内容加回来

先读取该候选人真实的数据库、历史队列、材料文件和沟通来源。按岗位及联系轮次建立可靠关联，不按标题相似就合并，也不把同一运行里的所有产物都分给每个岗位。

| 必须核对并恢复的内容 | 在详情里至少能看到什么 |
|---|---|
| 以前写好的招呼语 | 各次保存的准确全文、版本、对应岗位、可确认的起草或修改时间、复核意见。旧稿和当前稿都保留，不能只显示生成模板版本。 |
| 以前写好的简历 | 对应岗位的简历文件、可读的成品预览、版本、复核结果及附件引用。当前文件与历史文件有区别；若只有引用却找不到文件，显示“文件暂时无法读取”。 |
| 拟投递安排 | 准备投哪个岗位、用哪版正文和哪份附件、还有哪些步骤待完成；计划时间只在已保存时显示。没有发送证据时仍是计划。 |
| 本人的历史决定与批准 | 原话或可回查记录、所指岗位、准确正文及附件版本、决定含义和真实时间。文案接受、岗位兴趣与发送批准分开保存和展示。 |
| 实际发送的招呼语或回复 | 当时真正发送的准确全文、渠道、接收方、发送时间、业务结果与回读依据。不能拿当前草稿或获批稿替代实际已发文本。 |
| 实际发送的简历 | 实际附件文件及版本、对应岗位、发送时间与核验依据。准备好简历不等于发出简历，不能把附件引用当发送证据。 |
| 双方沟通记录 | 每条可获得的消息原文、发送方、真实时间、相关附件和来源；索要简历、实质回复、面试安排和待回复事项能够点开查看。 |
| 过去的工作与失败记录 | 做过哪些事、产物在哪里、哪些检查通过或失败、是否中断、是否待本人处理。旧运行和旧联系轮次仍可回查。 |

“应恢复”指把已存在且可核对的记录重新接入面板，不是事后编造。逐项区分：已读取并展示、源中不存在、源暂时无法读取、尚未接入、无法可靠关联。源中缺少旧版本就明确说明；不要重新写一份招呼语或简历来冒充旧产物，不补写过去的批准、执行或沟通事实。

宿主须保存各项材料的实际来源与岗位/轮次关联。源数据、材料文件和真实通信继续保存在用户私有环境；公共修订说明不附真实正文、简历或数据库。不要为了补面板把它们上传公共仓库。

## 修订完成后如何交付

- 给本人一份逐项核对清单：上述八类内容各自已恢复多少、哪些有缺口、缺口原因及对应岗位。计数来自实际核对，不把未读取当成零条。
- 在 Muse 的实际交互面板中打开岗位，验证能查看旧招呼语全文、打开旧简历、看到拟投递内容、核对实际已发内容及双方沟通原文。若该岗没有其中某类事实，显示准确原因。
- 切换岗位、关闭再打开详情后，历史版本和产物仍可访问；页面重做不覆盖旧稿、不丢联系轮次、不将未知结果写成成功。
- 说明哪些文字已改、哪些历史已补回、哪些还没接入。无法从当前来源验证的部分明确保留缺口，不能笼统称“全部补齐”。

本次是修订展示与历史接入，不授予招聘发送权限。待办按钮仍按 [Muse 面板接入要求](polling-console.md#muse-交互式面板) 调用已有业务服务，准确正文和实际附件的逐项批准及发送回读要求不变。不要为验收试发招聘消息。
