# 外联（打招呼）批量审批：设计稿

状态：已评审（2026-10-15），按测试先行实现。

## 要解决什么

一次给 25 个岗位打招呼，同时守住三条：

1. 每一条发出去的话，人都看过原文并明确同意；
2. 发送节奏不超过平台能接受的量，撞到风控就停；
3. 发过什么、发给谁、结果如何，都有不可改写的记录。

现在的缺口：消息没有数据结构，批量审批只有契约，发送不留审计，没有每站每日上限，多个会话可能同时操作同一个站。

## 不做什么

- 不模仿人类行为来躲避平台检测：不做随机轨迹、模拟打字、伪造设备特征，也不在风控提示后换方式继续。节奏限制是**上限**，用来守规矩，不是伪装。
- 仓库不驱动浏览器。实际点击发送仍由宿主（Claude in Chrome）完成，仓库只决定“这一条现在能不能发”，并记账。
- 不自动生成招呼语。宿主按 message-generation.md 起草，仓库只校验。
- 不把“审批了 25 条”当成“发 25 条”：每条发送前仍要逐条复核。

## 整体流程

```text
宿主起草 25 条招呼语（每条绑定一个 JOB_*）
        │
        ▼
outreach draft-batch drafts.json ──► 校验：职位已入库 / 未联系过 / 字数 / 证据已确认 / 外联规则
        │                              不合格的逐条退回，写明原因
        ▼
outreach ask BATCH_…  ──► 给人一张编号清单：平台｜公司｜岗位｜原文（逐字）
        │                  只提问，不算审批
        ▼
人回答，例如“发 1-20、23”
        │
        ▼
outreach approve BATCH_… --request ASK_… --items 1-20,23 --answer "发 1-20、23"
        │  核对：提问确实存在、提问之后清单没改过、所选编号都在清单里、原话非空
        ▼
┌──────────────── 宿主逐条发送循环 ────────────────┐
│ outreach next --platform boss --session S        │
│   仓库判断：本会话持有该站租约？审批仍有效？       │
│   这条还没发过？今天该站没被叫停？                 │
│   离上一条已满最小间隔？今天该站没到上限？         │
│   → 给出下一条可发的，或说明为什么现在不能发       │
│                                                   │
│ 宿主：打开会话 → 查重（已有我方招呼就不发）        │
│       → 插入原文 → 核对一致 → 点一次发送 → 确认送达 │
│                                                   │
│ outreach record ITEM --result sent | duplicate |  │
│                 failed | intervention --reason …  │
│   intervention：该站当天叫停，后续 next 一律拒绝   │
└───────────────────────────────────────────────────┘
        │
        ▼
outreach status BATCH_…  ──► 已发 / 跳过（重复）/ 失败 / 因风控停止 / 未发
```

## 契约（新增 `schemas/outreach.py`）

| 名称 | 作用 | 要点 |
|---|---|---|
| `OutreachDraft` | 一条待发首条招呼 | `job_id`、`platform`、`text`、`evidence_ids`（文中有实质主张时必填） |
| `OutreachPolicy` | 外发规则，参与摘要 | 每站每日上限（默认 50）、最小间隔 ≥30 秒、每批 ≤50 条、风控后不重试、撞风控当天叫停该站。上限只能调低，不能超过默认值 |
| `OutreachBatch` | 一批清单 | 每条有自己的内容摘要（职位 + 原文），整批有清单摘要 |
| `OutreachAsk` | 摆给人的问题 | 绑定清单摘要与规则摘要；逐字列出每条原文 |
| `OutreachApproval` | 人的决定 | 所选编号、人的原话（逐字）、对应提问、通道（终端 / 中继），沿用现有 `ApprovalChannel` |
| `OutreachAudit` | 每次尝试一条记录 | 只追加；结果为 `sent` / `duplicate_found` / `failed` / `intervention`；记录审批编号与通道 |
| `PlatformHalt` | 某站当天叫停 | 由 `intervention` 自动写入，当天不可撤销 |
| `SiteLease` | 站点租约 | 一个站同一时间只允许一个会话发送，默认 30 分钟，可续期 |

## 校验规则（`draft-batch` 时）

- 职位必须已入库，且平台与职位来源一致；
- 同一职位在审计里已有 `sent` 或 `duplicate_found`，退回，不再进清单；
- 首条招呼的写法规范见 [message-generation.md](../skills/job-hunting/references/message-generation.md)「首条招呼」，其中字数、数字、黑名单由仓库确定性检查；
- 引用的证据必须是已确认证据；
- 清单内同一职位不得出现两次。



## 发送前复核（`next` 时）

每次发送前都重新检查。任何一项不满足，就返回“不能发”及原因，绝不放行：

1. 本会话持有该站租约；
2. 审批覆盖这一条，且清单与规则摘要没变（变了就是 `STALE_APPROVAL`）；
3. 审计里这一条没有终态记录；
4. 该站今天没被叫停；
5. 距该站上一条外发满最小间隔；
6. 该站今天的外发数未到上限。

## 存储

新增迁移 `0004_outreach.sql`：草稿、批次、提问、审批、审计（只追加）、叫停、租约，共 7 张表。审计不提供删除或更新路径。

## 命令

`jobagent outreach draft-batch | ask | approve | next | record | status | lease`，全部登记进能力目录。

## 对现有内容的影响

- `generate`（消息）仍是“未开始”：宿主起草，仓库校验；
- `BatchApplication` 契约不变，外联不复用它，因为投递包含简历，外联不含；
- 巡检技能（仓库外）后续改为调用这些命令，以本地数据库为准，数据文档只作展示。

## 已定事项

1. 每站每日外发上限默认 50（平台自身限额优先，撞风控当天叫停）；入库目标同样按每站 50 规划，由找岗位环节单独实现。
2. 最小间隔 30 秒(2026-10-19 由用户从 120 秒调为 30 秒,固定间隔,不随机、不连发)。
3. 首条招呼规则写入 message-generation.md，并由仓库检查。
4. 本模块只管首条招呼。第二条及以后的问答式回复属于对话环节，另行设计；在那之前，回复仍逐条经人确认后发送。
