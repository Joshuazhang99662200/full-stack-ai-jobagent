# 人工加岗到下一轮策略的接线设计（已批准）

日期：2026-10-28。已核实PR #4合并至main，提交c7352a1969d5c4c7a9fa38a15f4c16bb36533c5d。当前源码与该main的文件树无差异。用户已批准本设计。实现与迁移说明见 docs/muse-manual-intake-2026-10-28.md；没有修改Muse私有任务。

## 问题与成功标准

用户在当前对话、消息列表或卡片中指定新岗位后，系统应持续保存并处理，不能只做一次性起草。目标链路：人工输入 → 可恢复队列 → 目标消歧与取完整JD → 原文快照 → 招呼草稿/独立复核，同时将有据的明确兴趣信号接到特征、词库与下一轮查询计划。

只有岗位被人工提供并不必然意味着喜欢该方向。采集来源、本人兴趣、文案决定、发送批准各有独立语义；明确“加入我的目标岗位/这是我想投的方向”才计兴趣正例，“看看这个/解释这个职位/帮我起草”只授权相应处理，不能静默扩展成长期兴趣。可保存原话与原始意图，后来明确喜欢后再追加信号。

用户无需重复说第二遍；身份已明确且读取获授权时，宿主自动执行可完成的只读采集、草稿准备与学习步骤。只在身份歧义、缺完整JD、缺独立复核或门控时返回具体待办。发送仍需逐项审批。

## 已有代码与Muse回复需要纠正的点

| Muse说法 | 核实结果 |
|---|---|
| 没有“人挑好”信号 | SearchSignal已有user_added，并映射owner_preference=like；需本人明确兴趣原话。缺的是入口自动记信号与持久消费，不能另加同义human_picked制造两份正例 |
| draft-batch先有审批单再起草 | 现有命令消费宿主已经生成的全文，校验成batch，然后ask/approve。它不负责生成，也不需要事先批准 |
| 未点Accept之前词库就是0 | 客观count来自选中完整快照；偏好权重才来自明确本人判断。Accept文案与岗位兴趣分开是既有正确规则 |
| 一定要3个人挑岗位才可组合 | 现有默认是2个独立公司达到repeated/可探索，3个为stable；三条方向负例是另一条降优先级规则，不应混用 |
| 特征校验失败就不能进词库 | 无效模型提案不得入库；有原文依据的确定性fallback仍可入库。零特征则标needs_seed/无可用特征，不能编词 |
| 写一句已进下一轮策略即可 | 必须保存并反查signal/feature/lexicon/plan标识，且区分候选、延后和实际入选查询，最后宿主真正消费该计划 |

PR4包含宿主协议，不包含Muse运行时插件或对话事件订阅。未连接Muse私有环境，无法核实其queue.jsonl、lexicon-private-v1.md、旧任务版本和实际调用日志。

## 方案取舍

1. 推荐：复用现有原子能力，补一个小型持久入队与推进协议。库保存事实和可恢复待办；Muse完成网页、模型生成与卡片交互；每步回填经校验的结果与证据。
2. 仅修改Muse提示词并约定JSONL：实施较快，但中断恢复、重放与版本冲突仍靠宿主自觉，无法从代码保证闭环。
3. 通用Agent/ReAct工作流框架：会增加依赖，仍需实现同样的队列事务与宿主适配，当前没有必要。

采用方案1，不重写发送或搜索核心。queue.jsonl可以作为兼容导出/人工阅读视图；唯一可写状态权威是同一私有SQLite账本，避免两份队列漂移。

## 队列结构与推进

拟新增 schemas/job_intake.py（类型）、jobs/job_intake.py（纯推进）、storage/job_intake_repository.py（追加事件与CAS）、cli/job_intake.py（宿主输入与现有库装配）。不新增浏览器/模型SDK到领域层。

队列条目至少保存：
- intake_id、candidate_id、来源manual/search、platform、原始消息引用与时间、本人原话的私有引用、意图/兴趣决定。
- 已知source_job_id/URL或待解析引用；job_id允许在消歧前缺失。编号35必须绑定实际列表版本与岗位身份，不能跨轮按旧编号猜测。
- 当前步骤、expected_version、快照ID/hash/version、特征版本、信号ID、词库摘要、下一轮plan_id与候选/入选/冷却状态。
- 草稿/复核/批次/审批/发送审计/跟踪引用；失败原因、待操作、暂停或关闭状态；所有结果引用现有真实对象。

入队对原消息ID+候选人+岗位幂等；同岗新消息追加引用而不复制职位或增加count。未知岗位先持久化入口，再解析身份。已联系岗位转到既有对话流程，允许学习其JD，不再次生成首招。

基本推进：
pending_identity → snapshot_pending → snapshot_complete
之后分两个可恢复分支：
- 草稿分支：draft_pending → review_pending → approval_pending。宿主按完整JD和已确认证据生成全文、独立复核，再复用draft-batch/ask。批准、租约、发送与跟踪只是现有对象投影。
- 学习分支：features_pending → signal_pending（仅明确兴趣）→ lexicon_pending → plan_pending → strategy_recorded。没有明确兴趣可抽取客观特征，但偏好不加分；没有成熟词或冷却中仍保留候选，不能承诺入选下一轮。

不把两个分支硬塞到一个单向枚举。学习冷启动不能无故阻断一个已有完整JD、可接地且通过独立复核的草稿；生成草稿也不能被当成已经完成策略更新。

每次next动作返回实际输入契约、来源引用、幂等action_id与阻塞原因。回填时以existing snapshot/features/batch/plan为证据，由核心读取验证，不能靠传布尔done=true完成步骤。事务和expected_version拒绝过期写入；重启后从未完成步骤恢复，不重复采集、记信号或生成新批准。

## 与现有能力的具体衔接

1. 身份明确后取JD前复用sourcing预算，人工岗位同样占详情尝试，不伪造查询；保留platform=boss/zhilian等，发现归因manual。
2. 全文按JDSnapshot原样保存；partial/listing卡在snapshot_pending，不生成首招或学习特征。JD更新使相关旧特征/草稿/计划待重算；旧人工审批仍由现有摘要门禁判断，不继承给新正文。
3. factorize复用现有原文证据校验与fallback。信号features从持久化feature_set绑定到准确JD，引文和所有反馈均能反查原消息。
4. 明确兴趣写既有user_added；文案Accept/Revise仍记message_feedback。本人撤回兴趣追加neutral，不删除旧事件。重复投递/采集不重复奖励。
5. lexicon-update包含该域全部选中有效最新快照和当前本人信号，不能只传新来的一个岗位而重算丢掉旧样本。
6. 保存版本MD并原子更新活跃摘要，回读一致后生成并持久保存CombinationPlan。
7. 下一轮搜索任务必须读取活跃plan_id，将实际搜索query_hit和预算行动绑定回同一计划。计划生成、任务领取、实际执行是三个不同事实；搜索失败/冷却不算已执行。
8. 卡片回执保存用户对准确条目的决定，发卡不等于批准。获批发送与readback成功之后再接tracking start。已发条目的新来信走conversations，不误进首招队列。

沿用每站每轮3查询/20详情尝试、每日最多50详情尝试和本人硬条件。人工塞入多个岗位也不能新增一套不受限详情额度。

## 人工正例成熟度

推荐本次仅补接线，保持现有2独立公司可探索、3公司stable、本人种子可冷启动；一岗只记一次，单样本不能置顶，重复同公司不增加独立公司数。若要求“3个不同人工选中岗位且不同公司才增强优先级”，应另设明确策略并写测试，不将其误用为客观count或“三名用户”，也不跨候选人聚合私人偏好。

客观出现次数、本人正例支持数与派生权重必须独立报告。任何批准招呼的动作都不能隐式提升岗位偏好。

## 宿主回执与真实验收

回复用户须提供可追溯状态，例如：
“已入队；全文已保存；特征已提取；本人的兴趣选择已记录；词库版本vN；计划P已生成。该特征目前只有一个独立样本，保留候选，本轮未提升优先级。”
尚未执行的步骤必须如实显示待办，不能一概写“已进下一轮搜索”。计划已生成不代表Muse定时任务已领取。

单测/集成验收至少包括：
- URL、列表编号、对话卡片三个入口；不明确身份只入待消歧，不猜岗位。
- 相同消息/岗位重复触发、同岗多来源、CAS并发和中断恢复不重复计数。
- partial JD阻断、原文变更失效、门控暂停、人工岗位正确占预算。
- 明确兴趣user_added、不明确参考无偏好、仅Accept文案不加岗位偏好。
- 快照→features→signal→lexicon→plan都有真实绑定引用；更新一个岗位保留旧域样本。
- 词库提交中断不留下半写MD；计划可恢复、可反查，下一轮实际领取新计划。
- 两个分支分别推进；弱/硬条件不通过不可假装通过；没有证据或复核不能生成有效待批条目。
- 已联系岗位不重复首招；所有发送路径依旧要求批准/租约/next/readback。
- 两轮合成流程：首轮从聊天人工加岗，第二轮读取由其有据反馈产生的新计划；未执行查询不伪造日志。
