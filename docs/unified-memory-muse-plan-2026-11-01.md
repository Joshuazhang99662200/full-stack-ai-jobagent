# 统一记忆闭环：代码实施、Muse 资料清单与接入规划

**状态：总体方案，第一期已在本地实现并通过回归验证。** 实际参数与接入边界见 [第一期说明](unified-memory-p1-2026-11-02.md)。下文保留完整目标；P2–P4、实际模型消费、反馈关联、运营分析和 Muse 联调尚待完成。不迁移 Muse 真实数据库，不发送招聘消息。本地未推送的代码不能当成 Muse 已能获取的 GitHub 版本。

**目标：** 让真实反馈能进入下一次搜索和起草，并能检查改动后的实际效果。每次任务都能回答：读了什么记忆、带入了哪些规则、产出了什么、后续结果怎样。

**实现方向：** 复用现有私有 SQLite、偏好文件、搜索学习、改稿与漏斗分析模块，补一层统一服务和调用记录。不重建一套岗位数据库，不把候选人的事实、个人偏好与推测混成一份长文，也不以向量数据库作为首期前提。

本文面向代码维护者和 Muse 接入者，其中的接口、字段及执行说明不放进普通用户页面。

## 二、统一结构与责任边界

```mermaid
flowchart LR
    A[真实选择、改稿和沟通结果] --> B[既有私有业务记录]
    B --> C[统一来源索引与记忆快照]
    C --> D[按本次任务选择上下文]
    D --> E[Muse 搜索或起草]
    E --> F[输入与产物关联记录]
    F --> G[搜索效果、文案反馈与转化复核]
    G --> H[下一版软策略或待确认规则]
    H --> C
```

### 四类内容分别保管

1. **事实**：完整 JD、已确认候选人证据、准确草稿、本人原话、实际发送与回复。原有领域服务继续负责；记忆系统只引用，不改写。
2. **学习结果**：偏好假设、关键词支持与反例、文案修改模式。保留出处、适用范围及版本，不能拿自己的旧总结作为新证据。
3. **有效规则**：已有本人确认或既定政策允许生效的内容。搜索软优先级沿用现有学习政策；新增长期文案规则、硬条件调整仍走既有本人确认流程，不能混在一次文案 Accept 里批准。
4. **效果记录**：本次选取与注入了哪些内容、用了哪版材料、后续观察到什么结果。只保留关联和证据，不再维护一套相互覆盖的业务当前态。

统一服务负责组织，不成为第二个数据库权威。动态配置继续以 `rules effective` 的当前确认档为准；已发送、已关闭及旧版本不追溯改写。

### 冲突与不完整数据

- 候选人事实不被偏好或诊断修改；岗位要求不变成候选人能力。
- 明确硬条件优先于学习得到的软偏好；新旧规则范围不一致时不能只按“更新时间更晚”覆盖。
- 适用规则冲突、版本过期、材料缺失时，仅阻塞受影响步骤，报告具体原因，不重开参数初始化表单。
- 原始文案接受、岗位兴趣、发送批准及实际发送分别记录。没有回复不是岗位负例，登录失效也不是文案效果差。
- 不能可靠关联岗位、联系轮次或发生时间的旧记录，保留为待核对来源，不冒充已学习样本。

## 三、代码准备怎样实现

以下表格描述完整目标，部分路径和类型仍属拟新增设计。第一期只实现来源、快照和上下文，实际清单以第一期说明和代码为准。模型统一放在 `schemas/`，其他层只消费，不复制定义。

| 层 | 拟新增或修改的文件 | 责任 |
|---|---|---|
| 契约 | `src/jobagent/schemas/memory.py` | 定义来源引用、快照、上下文请求/结果、注入与结果关联、诊断状态 |
| 领域规则 | `src/jobagent/memory/selection.py` | 按候选人、任务、岗位、渠道和适用范围筛选，处理冲突与失效；不依赖 SQLite、CLI 或平台 SDK |
| 应用服务 | `src/jobagent/memory/service.py` | 调用既有存储和学习模块，组装统一快照与上下文；通过端口访问外部能力 |
| 端口 | `src/jobagent/memory/ports.py` | 定义来源读取、快照存储、产物检查、推理适配所需的接口 |
| 私有持久化 | `src/jobagent/storage/memory_repository.py` | 第一期使用独立私有元数据快照库，不迁移业务数据库；使用/结果关联尚待后续实现 |
| 现有模块适配 | `src/jobagent/bridge/memory_sources.py` | 对接偏好和已确认规则的只读来源；词库和指标消费者待后续实现。领域核心不依赖 SQLite |
| CLI | `src/jobagent/cli/memory.py`、`src/jobagent/cli/app.py` | 暴露统一调用，复用错误处理、私有路径和候选人隔离要求 |
| 宿主接入 | `hosts/personal-ai/memory.md`、`hosts/personal-ai/tasks.md` | 明确何时调用、读取哪些输出、如何恢复与回填 |
| 能力声明 | `skills/job-hunting/references/capability-catalog.md` | 逐项登记真实落地状态；测试约束声明和实际入口一致 |

第一期快照库拥有独立格式，不沿用业务库迁移编号。后续如需改业务表，迁移编号以实施时仓库最新版本顺延，不直接对未知版本的 Muse 库执行迁移。

### 拟新增契约

| 类型 | 必须表达的信息 |
|---|---|
| `MemorySourceRef` | 候选人、来源类型及原始记录引用、版本或摘要、可靠的岗位/轮次关联、来源状态、发生时间是否已知 |
| `MemorySnapshot` | 不可变快照 ID、父版本、来源集合及摘要、各学习模块版本、有效规则引用、冲突和缺口、编译时间 |
| `MemoryContextRequest` | 候选人、任务类型、快照、可选岗位与渠道、当前动态规则版本；任务使用当前版本，不静默消费过期快照 |
| `MemoryContextBundle` | 选中的事实与规则引用、适用建议、支持与反例、排除理由、上下文摘要、是否可供该步骤使用 |
| `MemoryApplication` | 任务与上下文 ID、实际输入摘要、产物引用及摘要、适配器版本、哪些规则只是建议、注入证据等级 |
| `MemoryOutcomeLink` | 对应任务/产物及真实反馈、业务结果或指标记录的引用；未知结果继续标未知 |

所有写入携带幂等 ID 与预期版本：同号同内容重放不重复学习，同号异内容拒绝；并发冲突要求重新读取。读取不消费搜索额度，记录学习也不冒充查询、批准或发送。

“选中规则”“送进模型”“模型实际遵循”“带来更好结果”是四件事。宿主只说自己用了某条规则时，记为 `host_reported`；受支持的适配器实际检查调用输入与产物绑定后，才能记为 `adapter_verified`。后者证明输入接入，仍不证明模型遵循或结果改善。

### 拟新增的统一入口

前三项属于第一期实现，具体边界见第一期说明；后三项尚未实现，不可调用。完整目标必须逐项提供同版本帮助、JSON Schema、错误结果及测试，不能以三个查询入口替代整条闭环。

| 拟定入口 | 行为与副作用 |
|---|---|
| `memory status` | 只读：查询来源、快照、待确认规则、使用及结果关联覆盖情况；缺失、未接入与成功空结果分开 |
| `memory compile` | 第一期只校验已有来源并保存不可变元数据快照；不重算偏好或策略、不调用模型、不提出或批准规则 |
| `memory context` | 只读：按任务确定性筛选受支持范围，并重查来源新鲜度；旧快照保留追溯，不提供跳过来源核验的历史上下文开关 |
| `memory applied` | 写关联记录：检查实际请求与产物引用，登记注入证据等级；不声称已经取得业务效果 |
| `memory link-result` | 写关联记录：绑定已保存的真实反馈或业务结果，不创建虚假的发送、回复或本人决定 |
| `memory analyze` | 调用已有指标、诊断及效果复核服务，保存分析关联；来源不足时返回观察或未接入，不让 LLM 捏造比率 |

`MemoryService` 对应提供 `status`、`compile`、`context`、`record_application`、`link_result`、`analyze` 六个应用入口。CLI 和宿主适配调用同一实现，不能各写一套规则。

首期上下文任务只接 `search` 和 `greeting`。`reply`、`resume` 在对应消费者和测试完成前返回 `not_integrated`，不能用招呼语上下文替代后宣称已支持。

## 四、统一实施顺序

每期独立验证和交付；先完成可追溯的一条链，再扩展任务，不一次改完所有模块。

### P0：Muse 资料与来源对账

- [x] Muse 已提供首批七类说明与补充材料；来源强度、缺失和待核对项已分别登记，材料到件不等于真实来源验证通过。
- [ ] 在只读状态下对照现有契约，形成来源映射和缺口清单；不先修改私有快照结构来迁就接口。
- [ ] 合成案例覆盖岗位喜欢但修改文案、重复事件、旧稿及发送结果未知，固定预期行为。

**交付：** 双方认可的来源映射；能分清旧数据事实与宿主推断。此阶段不声称形成学习闭环。

### P1：统一记忆查询、快照与按任务选择

- [x] 在 `tests/memory/test_context.py` 与独立边界测试中验证跨候选人拒绝、缺失诊断、同编号规则冲突、读取不写业务状态及准确确认链。
- [x] 新增第一期契约、确定性选择、私有来源适配、独立元数据快照库及前三个 CLI 入口，复用现有规则仓储与偏好解析，不删除旧调用路径。
- [x] 验证同来源编译幂等、来源变化时旧上下文失效、快照元数据可追溯；这期不保存历史正文副本，不提供跳过新鲜度检查的旧正文重放。

**交付：** Muse 能清楚查询“目前有哪些记忆”并为搜索/招呼语取得可核对上下文。

**本地验收：** 完整回归 1842 通过、2 项符号链接创建权限跳过；随后新增的 3 项无效 JSON 来源用例通过。Ruff、mypy 和差异检查通过。对用户交付的文档做本地私有副本盘点，12 个来源可读、1 个完成重放材料缺失；重复编译幂等，说明材料不会被提升为可用规则。此项仅验证本地文件及适配器，Muse 真实运行验收仍未完成。

### P2：接入搜索和招呼语的真实消费

- [ ] 在 `tests/memory/test_applications.py` 写失败用例：只选中未注入不能记已使用、同一上下文绑定错误产物拒绝、只反馈文案不能改变岗位偏好。
- [ ] 搜索接入现有 `IntakeStrategyService` 的策略重建、领取和实际查询归因；任务生成计划不等于执行搜索。
- [ ] 起草适配器将统一上下文带进模型输入，保存请求摘要与准确草稿；本地 CLI 和 Muse 分别验收。
- [ ] 新增 `applied`、`link-result`，验证接受文案不会批准发送，输入或正文改变后旧绑定不可复用。

**交付：** 用合成数据演示反馈产生变化、变化进入下一次输入、新产物可追溯。不以模型生成一段“已学习”作为验收。

### P3：运营分析和规则效果复核

- [ ] 在 `tests/memory/test_effects.py` 写失败用例：没有真实结果不记成功、重复联系不混算、零分母为未知、摘要不能充当发送证据。
- [ ] 新增 `analyze`，复用 `PipelineMetricsService` 和 `PipelineRuleService`；分析口径、来源及优化前后版本均可反查。
- [ ] 诊断产生规则建议，经本人确认后进入下一版上下文；无效改进只产生回滚提案，不自动撤销规则。
- [ ] 验证现有平台和切片范围。当前运营平台契约主要为 BOSS/智联，薪资分桶也有固定口径；不支持的渠道或口径明确拒绝，扩展须另改契约及测试，不能静默换算。

**交付：** 能解释“哪一版改动，在怎样的数据范围内，观察到什么变化”，不把相关性写成因果证明。

### P4：回复、简历与宿主验收

- [ ] 分别接入回复和简历消费者，先写任务隔离、准确材料版本及证据不被偏好改写的失败测试。
- [ ] 在 `tests/cli/test_memory.py` 验证所有公开入口与能力目录一致，旧入口不启用时保持兼容。
- [ ] Muse 实际验证重启恢复、并发、失败重放和两个连续周期的真实读取回执；没有获批发送也能完成主体接线验收。

**交付：** 分别标出已接通任务和未接通任务，不以搜索和招呼语的成功替代全部材料的验收。

每期遵循“写失败测试 → 确认预期失败 → 最小实现 → 相关测试 → 全套门禁”。实施时按 [贡献指南](../CONTRIBUTING.md) 依次执行 pytest、Ruff、mypy 和差异检查；迁移另需备份、临时副本验证与恢复测试。只有用户要求提交/推送时才执行 Git 交付。

不要把凭证、Cookie、真实履历、联系信息或整库上传到公共仓库。Muse 向代码维护者交付脱敏结构、必要合成样例和缺口汇总；真实记录在其私有环境原地验证。仅提供一段“已接通”说明不算资料齐全。

## 六、Muse 现在怎么调用

第一期的三个入口按专页接入。学习重算、规则确认、策略执行和指标分析继续使用下列已有服务；尚未实现的统一写入口不能提前调用。命令的输入契约和参数以当前固定 SHA 下的 `--help` 及 `schemas/` 为准。

注意：部分现有 CLI 经 `open_database` 自动迁移数据库，命令名称只读不代表初始化无写入。P0 来源盘点先使用只读数据库连接和安全的帮助查询；未确认实际库版本、备份和迁移路径前，不直接对 Muse 真实库试跑这些入口。

| 场景 | 已有入口 | 宿主还要做什么 |
|---|---|---|
| 读取已确认动态配置 | `jobagent rules effective` | 复用已有初始化，不再询问已确认数字 |
| 对原始搜索信号求值 | `jobagent jobs learn-search` | 提供 `SearchLearningRequest`；这是计算输出，不代表宿主自动保存或搜索 |
| 重建、读取、领取下一轮策略 | `jobagent intake strategy`、`active`、`claim` | 用真实私有词库/请求，绑定寻源轮次；实际查询后 `record-search` 留回执 |
| 保存改稿差异与提案 | `jobagent host message-diff`、`diff-report`、`rule-propose` | 保留准确前后文及本人来源；归纳不等于批准 |
| 取得已确认文案规则 | `jobagent host confirmed-rules` | 宿主在起草前主动读取并带入模型上下文；当前不保证所有入口自动注入 |
| 算转化、诊断和效果复核 | `jobagent pipeline metrics`、`diagnose`、`rule-review` | 先保存真实事实、指标及其引用，规则确认继续走既有入口 |

本地 `greetings generate` 的可选偏好配置由已有代码支持，但调用依赖其本地模型适配，不能作为 Muse 默认前置。Muse 有自己的模型时，应提供符合现有 `ReasoningProvider` 边界的适配，或由宿主模型产出契约化结果后交核心验证；不能仅因返回 JSON 就宣称完成独立复核或本人认证。

## 七、统一入口落地后，Muse 怎么调用

以下是完整目标顺序。当前仅有第 1、3、4 步的第一期查询与快照能力；第 2、5 步继续走现有业务链，第 6–8 步的统一入口尚待实现。不能把这份顺序直接当作全部可执行脚本：

1. **恢复任务**：固定仓库版本，加载候选人、私有配置和初始化记录，调用 `memory status`。必要来源没接通时说明缺口，不能自动拿空记忆继续冒充完整学习。
2. **接收真实事件**：先调用已有业务服务保存本人选择、改稿或沟通事实，再让记忆索引引用这些记录。按钮点过不等于反馈已持久化。
3. **更新快照**：来源发生变化时调用 `memory compile`。事实与派生分开保存，同一输入幂等，不把每次刷新都当新样本。
4. **任务前取上下文**：调用 `memory context`，显式指定任务与适用岗位。搜索读取搜索偏好，起草读取文案规则和已确认证据；不把全部历史塞进每次提示词。
5. **实际调用模型或搜索流程**：上下文只是输入，LLM 自由组织搜索建议或文案；确实派发平台读取仍走预算网关，发送仍走逐项审批。
6. **登记输入与产物**：调用 `memory applied`，提交实际输入和产物引用。宿主声明与适配器验证分级，不把“准备过上下文”写成“模型已采用规则”。
7. **关联后续反馈与结果**：真实修改、本人决定、发送回读或招聘方回复保存后，调用 `memory link-result`。不能把一次 Accept 当成岗位喜欢、发送批准和有效转化三份正例。
8. **运营复核**：按本人已有周期或显式请求调用 `memory analyze`，比较适用规则前后及当前累计数据。没有现成频率配置时不私自创建定时任务。

每次调用检查业务结果，保存请求 ID、候选人、版本及回执。中断后从已保存步骤恢复；结果未知先核对，不自动重复有副作用的调用。规则变动按既有通知与确认协议处理，不擅自重问配置或激活新硬条件。

## 八、怎么嵌入 Muse 和现有面板

### 后端与模型分工

- 有 Python 时，在宿主私有环境安装同版本核心。可进程内调用应用服务，也可通过 CLI；不依赖维护者的 localhost、本机浏览器或私有配置。
- 只有工具调用环境时，先确认实际可用的受支持工具适配。CLI 新增不等于 MCP 工具已注册；工具封装须另做相同隔离、幂等和回执测试，未完成前标未接入。
- Muse 的 LLM 负责理解反馈、提炼有来源的候选建议、选择表达方式和起草。核心负责版本、范围、引用、事实与审批门禁、持久记录和数值计算。
- 无可靠私有持久化时只允许会话内辅助，明确不能保证跨会话学习；不把临时聊天摘要宣称为长期记忆系统。

### 面板接线

“这版文案可以”“帮我改一下”“岗位不合适”等操作先进入各自真实反馈流程，保存成功后再更新面板与记忆来源。本人可查看原文和历史版本，关闭弹窗不能清除尚未保存的意见。

五列表格的“进展”继续由 LLM 根据实际记录自由写；它是展示摘要，不是学习样本或业务事实来源。审核视图继续先放 JD 要点和关键词，再放招呼语全文。不能把自动生成的进展再反喂为原始证据。

普通页面不显示记忆字段、SQL、取数公式和运行日志。若学习确实产生已确认变化，可简短说明与任务相关的结果；具体来源、使用版本和排查信息放在用户主动查看的详情中。

运营页面用可读标签解释真实分子分母、观察窗口、未知项和版本变化。不要只显示“提升百分之几”：应能看见它比较的对象，且不得把尚在等回复的岗位直接诊断为写作失败。

## 九、如何判断真的“越搜越准、越写越准”

| 目标 | 观察什么 | 不应混淆的情况 |
|---|---|---|
| 搜索更符合本人 | 明确喜欢/拒绝及理由、已核对完整岗位中的符合比例、不同查询的有效产出、覆盖与未完成范围 | 模型自己打高分不是本人更喜欢；没读到的岗位不当作不符合 |
| 文案更符合本人 | 有明确审阅决定的草稿、本人修改的类别与依据、重复出现的问题是否减少 | 改动少不必然更好；事实错误与文风修改分开；未审阅不记为接受 |
| 运营效果改善 | 已核实发送、已读、实质沟通、索要简历、简历发送和面试等阶段的可比转化 | 内容版本、渠道、观察时长和岗位构成变化会影响结果；不能把相关性当因果 |
| 记忆真正被使用 | 真实来源 → 快照 → 上下文 → 实际输入 → 产物 → 后续反馈的可回查链 | 有反馈计数、consumed 标记或一份总结文件，不足以证明进入下一次生成 |

搜索质量和文案审阅指标如无现成权威实现，应另立契约和测试后提供，不能让 LLM 现场算一个比率充数。指标窗口及阈值沿用已确认、实际受支持的配置；历史未保存时间不补造，零分母与缺失数据保持未知。

本方案不承诺每轮指标单调上升，也不涉及模型权重训练。这里的自进化是有来源、可撤回、能复核的偏好与策略改进，新的长期规则仍须按适用协议确认。

## 十、双方下一步交付

**代码侧：** 先完成 P1/P2 的搜索与招呼语最小闭环，输出契约、实现、测试、可用入口和迁移说明；再接 P3 分析、P4 回复与简历。每阶段声明支持范围，不把规划中的命令列成已落地。

**Muse 侧：** 先返回私有资料清单的前三项及缺口，并说明当前搜索、起草各走哪个入口；随后提供一次合成任务的输入、上下文、产物与保存回读证据。数据未对齐前不重写快照结构、不盲迁移，也不凭这份文档声称已完成接入。

**共同验收：** 至少一条反馈能改变下一次适用输入，下一次产物有来源；另有一条无关或不合法反馈被正确排除；重启后结果仍可读；运营结果可按真实范围复核。所有真实发送仍等待本人逐项批准，不能为打通飞轮而试发消息。
