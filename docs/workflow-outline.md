# 工作链路配图底稿

这份底稿根据本人对原流程的批注修订，作为 README 流程图的内容来源。它包含宿主责任、当前实现与已合入主分支的运营能力；版本范围和接入缺口见[流程实现说明](workflow-implementation.md)。

```text
1. 人机协同初始化
   |
   +-- 本人提供原始简历、补充经历和求职意向
   +-- Agent 整理材料，追问遗漏、歧义与冲突
   +-- 共同明确地点、薪资、岗位方向和排除条件
   +-- 检查宿主、Python、私有存储及恢复能力
   |
   v
2. 先确定每个站点的采集方式
   |
   +-- Agent 预检该站的浏览器与官方 MCP / API / CLI 能力
   +-- 向本人列出可用方式、可取得的字段与限制
   +-- 本人选择默认方式；可组合列表通道与详情通道
   +-- 预先验证列表读取、完整 JD 补齐、去重和入库
   +-- 只有列表时，走已允许且已验收的详情补齐路径
   +-- 登录、验证码、风控或限流：暂停，不换通道绕行
   |
   |   渠道探测和 JD 补齐是接入前置责任。
   |   已有补齐适配器可以复用；统一自动选择仍需补齐，
   |   不能把未实现的路径留给运行中的 Agent 临时拼接。
   v
3. 建立候选人证据库
   |
   +-- 解析简历并保留原文、页码和出处
   +-- 提取经历、技能、项目与成果，形成待确认草稿
   +-- Agent 将事实、硬条件和待补项整理为编号列表或 Markdown
   +-- 本人可一次确认清楚的一组，也可勾选、排除或更正
   +-- Agent 将这次明确确认的事实 ID 逐项写入现有确认入口
   |
   |   一份列表可以确认多项；不要求逐项聊天问答。
   |   更正或新增内容先更新草稿，未确认内容不进入对外材料。
   v
4. 每轮先恢复状态、处理已有对话，再补充新岗位
   |
   +-- 恢复上轮检查点，读取待批事项与已发送记录
   +-- 先读取招聘方新消息和本人已有的对话
   |     +-- 普通问答：AI 起草、复核，批准后发送
   |     +-- 要简历：进入第 7 步，核对交换条件
   |     +-- 面试、联系方式、offer、危险请求：交本人处理
   |
   +-- 对仍需新岗位的方向开展搜索
         +-- 从已确认证据、硬条件和搜索反馈形成查询
         +-- 按已选渠道采集，或接收本人提供的链接 / JD
         +-- 保存来源、时间、搜索词与完整性状态
         +-- 去重；已联系岗位回到已有对话，不再发首招
   |
   v
5. 完整 JD、筛选与匹配
   |
   +-- 先用列表字段排除明显不符合硬条件的岗位
   +-- 经前置验收的路径取得完整 JD，再校验正文边界
   +-- 提取岗位要求，对照已确认证据
   +-- 列出匹配理由、强项、缺口与风险，按档位排序
   |
   +-- 不符合：排除并保留原因
   +-- 待判断：交本人裁决
   +-- 适合：准备该岗位的招呼或继续已有对话
   +-- 缺完整 JD：保留未完成状态，不生成假合格的定向材料
   |
   v
6. 首次联系或继续沟通
   |
   +-- 完整 JD + 已确认证据 + 本人适用偏好
   |     -> AI 生成一岗一条的首招或上下文相关的回复
   |     -> 独立复核事实、岗位相关性与表达
   |     -> 展示准确全文，交本人审批
   |     -> 发送前核验，执行后回读与记账
   |
   +-- 无回复：按到期清单跟进，保留已读与未知状态
   +-- 明确拒绝 / 岗位关闭：记录原因，停止该轮推进
   +-- 对方提出交换简历或本人确认推进：进入第 7 步
   |
   v
7. 满足交换条件，才进入定向简历链路
   |
   +-- 触发条件之一：
   |     +-- 招聘方明确索取简历，包括平台的简历交换请求
   |     +-- 对方已有回复，本人确认有意继续并决定发送简历
   |     +-- 本人明确要求对某个岗位直接准备并提交申请
   |
   +-- 核对同一岗位、完整 JD、本人意向与当前对话
   +-- 基础简历 + JD + 已确认证据
   |     -> 定向改写
   |     -> 独立复核主张
   |     -> 程序校验，组装变体并计算 diff
   |     -> 排版，核对 PDF 正文、页数和实际版面
   |     -> 本人查阅并批准准确全文和实际附件
   |     -> 发送前再核验，执行 / 人工交接，回读并记账
   |
   |   对方索取简历不等于本人批准发送。
   |   平台上的“同意交换”也属于交付简历，需要批准。
   |   仅打过招呼或普通寒暄，不自动触发附件发送。
   |   换岗位、改正文、换附件或收到影响语境的新来信，要重新核验。
   v
8. 持续跟进与结果记录
   |
   +-- 对话按事件推进：已招呼、已读、初步沟通、索取简历、
   |   简历已发、待面试、已面试；废止原因单独记录
   +-- 面试邀约和敏感事项由本人接手
   +-- 保存真实回执、观察时间、规则版本和材料版本
   +-- 结果不明时先核实，不重复发送，也不补造中间阶段
   |
   v
9. 后阶段运营：看哪一段转化出现问题
   |
   +-- 招呼发出 -> 已读：观察触达
   +-- 已读 -> 初步沟通：观察回复转化与已读不回
   +-- 初步沟通 -> 索取简历：观察继续了解的意愿
   +-- 简历已发 -> 待面试：观察简历后的约面转化
   +-- 待面试 -> 已面试：观察后续推进
   |
   +-- 按平台、方向、技术、薪资段、招呼 / 简历版本切片
   +-- 核对同一联系轮次的分子、分母和来源证据
   +-- 区分岗位关闭、明确拒绝、缺证和取消等原因
   +-- 未知、不可观测或没有基线的项如实保留，不当成零
   |
   v
10. 诊断、规则改进与效果复核
    |
    +-- 比较历史基线、累计转化和连续窗口，生成诊断建议
    +-- 对问题段提出具体的招呼、简历或选材规则改动
    +-- 展示改动前后、依据、适用范围与规则摘要
    +-- 本人确认后，将规则纳入当前候选人的私有规则记录
    +-- 后续轮次读取有效规则，继续积累真实结果
    +-- 复核优化后表现：
    |     +-- 有效：保留规则与证据
    |     +-- 无效：形成调整、恢复或撤回提案，再由本人确认
    |
    +-- 搜索反馈另行更新下一轮查询与软优先级
    +---------------------> 回到第 4 步

贯穿全程：
  等待与中断保存检查点；恢复后重新核验产物和许可。
  资料确认、岗位选择、规则确认和发送审批是不同决定。
  新规则不能改写候选人事实，也不能替代具体消息与附件的发送审批。
```
