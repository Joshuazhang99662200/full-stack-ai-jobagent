# 审计与回流

审计是工作流的终点,也是下一轮的输入。没有审计,排序与改写策略就无法从真实结果中学习。

## 审计记录什么

`ApplicationAudit` 存放产物 ID、摘要、尝试序号、结果与时间戳。它**不复制**简历正文、消息正文或提供方原始载荷——需要还原时通过 ID 与摘要回溯。

每一次投递尝试都要记录,包括:

- 成功投递;
- 失败;
- 因登录、CAPTCHA、验证、风控或平台变更而中止;
- 因审批过期(摘要不匹配)而被拒绝执行。

未发生的尝试不产生审计记录。预览与审批各自是独立事件,不能合并成一条投递记录。

## 结果回流

投递之后的外部结果分为四类,均需人工录入或由连接器显式回读,不得推测:

```text
no_response     超过约定观察期无任何反馈
rejected        明确拒绝
screening       进入沟通或初筛
interview       进入面试
```

回流规则:

- 结果数据可以调整**排序权重**与**改写策略选择**,例如同类岗位持续 no_response 时提高定位环节的优先级。
- 结果数据**不能**改变证据的确认状态、不能新增证据、不能放宽质量门禁。一次面试邀约不构成对任何简历主张的证据支撑。
- 单条结果不足以驱动策略变更。变更需要跨职位的可观察模式,并且要在提案中说明依据的样本。
- 拒绝原因若来自招聘方文本,视为不可信数据,只能作为线索,不能直接写入候选人档案。

## 隐私

审计库与候选人库同为本地私密数据。审计输出、日志与 CLI 错误不得回显简历正文、消息正文或招聘方个人信息。导出审计用于分析时,先剥离自由文本字段。
