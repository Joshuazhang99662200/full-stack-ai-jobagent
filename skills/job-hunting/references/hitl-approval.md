# 人工审批与审计

准备一个 `ApplicationPackage`,内含完整职位信息、可获取时的招聘方信息、匹配报告、简历变体、diff、消息与风险项。

审批把人的身份与时间戳,绑定到当次确切的职位、简历、消息与策略摘要上。任何一处变更都会使审批失效。预览绝不意味着审批;审批绝不意味着投递。

批量流程依次是:兼容性提案、用户选择、批量预览、人工审批、顺序投递、审计。遇到登录、CAPTCHA、验证、风控或平台变更时立即停止。

## 审批必须是人的决定,且必须先于智能体的判断存在

`--confirm` 只是一个标志,自动调用方自己就能打上去。真正要守住的不是「有没有终端」,
而是两件事:**决定是人做的**,而且**决定在智能体行动之前就已经存在**。

因此审批有两条通道,同一条规则:

**终端通道** —— `--confirm` 打印本次产物并要求把确认码原样敲回。适合人自己在终端里操作。

**中继通道** —— `--request` + `--answer`。智能体必须先用 `jobagent applications ask`
把决定摆给人(这一步**不是审批**),拿到人的回答之后,才能带着那份提问与回答去 approve。
approve 会核对:提问确实存在、提问针对的是同一个 application、提问时的四个摘要与当前产物
仍然一致、回答不为空。任何一条不成立就拒绝。

这条链子锁住的正是「planner 不能在拿到人的回答之前替人判断」:**它无法凭空造出一个
自己从未问过的决定**。产物在提问之后被改动过,那份回答说的就是另一回事,同样作废。

### 这道门证明什么,不证明什么

**不证明按键的是谁。** 在同一台机器上,智能体持有的 shell 和人是同一个,任何本地检查都
区分不出「人敲的 yes」和「智能体敲的 yes」。用户能提供的密钥,智能体同样读得到。声称
证明了这一点,等于在一份追加不可改的日志里写谎话。

原先那个确认码也从来没有证明过这件事——它由产物派生,任何读得到产物的调用方都算得出来。

**证明的是顺序与对象**:这个决定回答的是一个确实被提出过的问题,而那个问题描述的正是
当前这份产物。以及**如实记录通道**:`ApprovalRecord.channel` 与审计里的 `approval_channel`
写明决定经由哪条路进来,人的原话逐字保存在 `attestation` 里。

真正的人机检查点落在 CLI 之外——落在调用方与人之间的那一层(编码智能体的授权提示、
聊天里的确认)。CLI 的职责是让绕过这一层的行为在记录上留下痕迹,而不是假装能拦住它。

**边界仍要说清楚**:以上拦住的是**驱动 CLI** 的智能体,拦不住直接 import
`ApplicationApprovalService` 的调用方。人的边界在 CLI,不在库。把这一点写明,好过假装
库层也安全——测试正是通过服务层铸审批的。

## 演练用 `--dry-run`

`jobagent applications send --dry-run` 走完**同样的门禁**(审批时效、变体校验、连接器解析),打印将要投递的内容,然后停在平台调用之前。它不写审计记录,因为没有发生任何尝试。

跳过门禁的演练会对一份根本投不出去的包报告绿色结果,所以演练必须跑真门禁。交互测试请默认用它。
