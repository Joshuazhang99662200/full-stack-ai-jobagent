# JD 来源与门控边界

定向改写必须有 JD 正文。各平台是否公开 JD **经过实测**,不要靠推测。

## 实测结果

| 平台 | JD 可否公开取得 | 依据 |
|---|---|---|
| 猎聘 | ✅ | 详情页服务端渲染,「职位介绍」 |
| 智联招聘 | ✅ | 详情页服务端渲染,「职位描述」 |
| LinkedIn | ✅ | 公开 `jobs-guest` 端点,`description__text--rich` |
| **BOSS 直聘** | ❌ | 未登录请求 302 到 `web/passport/zp/security.html` 安全验证页 |
| **前程无忧 51job** | ❌ | 搜索与详情接口返回阿里云 WAF 挑战 |

前三个用 `PublicPageJobDetailFetcher` / `LiepinJobDetailFetcher`,均**无需登录、无浏览器自动化、无 Cookie 复用**。

## 有边界的提取

每个招聘页都在 JD 旁边渲染绝不能进入 `jd_raw` 的内容:公司简介、防诈提示、「猜你喜欢」推荐位。把它们拼进去会静默污染需求抽取,而污染过的 JD 比没有 JD 危害大得多。

因此提取**两端都有边界**:`ExtractionRules` 给出起始标题与终止标题,连接器只提供自己的标题词与门控标记,切割、门控识别与长度校验统一在 `extraction.py` 里做一次。正文缺失或过短一律显式报错,绝不返回半截或掺料的 JD。

## 门控平台:实现为显式暂停,而非不实现

BOSS 直聘与前程无忧建模为 `GatedJobSource`。它们**不是没做**,而是做成了「检测到门控 → `USER_INTERVENTION_REQUIRED` + 给出人工路径」。这样链路完整,边界也看得见,不会退化成静默失败。

绕过这两个门控需要的是指纹伪装、stealth 浏览器、代理轮换或打码。**本项目不做这些**,`stop-conditions.md` 也明确禁止「更换账号或代理绕开」。

人工路径:

```powershell
# 你自己在浏览器里打开职位,复制 JD 正文存成 txt
jobagent jobs ingest-jd .\listing.json .\jd.txt
```

这条路径不抓取任何东西,也不绕过任何门控——你本来就有权看那一页。

## 用自己的登录态取数 ≠ 绕过反爬

这两件事必须分清:

- **正当**:用户自己登录、自己触发、单条读取自己有权访问的页面。猎聘官方 token(`liepin-cli setup`)就是这种形态。
- **不正当**:指纹伪装、stealth 浏览器、代理与账号轮换、打码。

BOSS 直聘**没有**官方 token 通道。社区方案(如 boss-helper)是浏览器扩展,其作者自己在 README 顶部警告「有一定风险(如黑号、封号、权重降低等)」,且该项目 LICENSE 声明 MIT 而 README 又写「禁止用于商业用途」,许可状态矛盾,不可复用其代码。

## 频率与条款

单条、由人触发。不做批量扫描。**LinkedIn 的服务条款对自动化访问远比国内平台严格**,在它上面尤其不得做批量抓取;guest 端点虽然公开,这条约束照样成立。
