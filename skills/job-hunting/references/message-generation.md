# 消息生成策略

首条招呼统一采用完整 JD、已确认证据与本人适用偏好生成全文并独立复核，不再调用历史挑句结构或首招字数硬上限。

投递消息(打招呼语、求职信、邮件正文)与简历受同一套证据规则约束。求职信是最容易出现编造的地方,因为它的文体鼓励概括与自我评价。

## 证据规则

- 消息中的每一条**实质性主张**都必须引用一个或多个 `EVID_*`,与简历条目同标准。
- 只能引用已被用户确认的 canonical Evidence。草稿证据可以进入提案,但必须在视觉上标注为暂定。
- 允许出现的无证据内容仅限于:意向表达、对职位的兴趣、可安排的时间、礼节性措辞。这些不是主张。
- 禁止把简历里已收窄过的表述在消息里重新放大。消息中的主张范围不得超过它所引用证据在简历中已通过校验的范围。

## 禁止项

- 不得凭空造出年限、规模、增长率、团队人数、营收数字。
- 不得把参与表述为主导,不得把协助表述为负责。
- 不得声称对该公司、该产品、该团队有实际了解,除非该了解本身有证据。
- 不得编造共同联系人、共同经历或推荐关系。
- 不得声称薪资预期、到岗时间、签证状态,除非这些取自候选人档案中的显式字段。

## 招聘方信息

- 只有当连接器实际返回了 `RecruiterInfo` 时,才使用招聘方姓名与职位。
- 招聘方信息缺失时使用中性称谓,不要猜测姓名、性别或职级。
- 不得把招聘方的个人信息写入日志、审计记录之外的任何位置。

## 语言与语气

- 消息语言跟随 JD 语言,除非候选人档案中的偏好显式指定了其他语言。
- 语气默认为简洁、具体、事实导向。长度控制在能被完整阅读的范围内。
- 不使用夸张形容词("顶尖""完美契合""极其擅长")。用可核验的事实替代评价性措辞。

## 首条招呼

宿主按 [greeting-writing.md](greeting-writing.md) 阅读完整 JD、已确认证据和本人适用偏好，重新生成一条完整消息，再独立复核。模型自行决定切入点、开头、背书、组织顺序与结尾，不读取旧话术库，不使用固定句子或固定结构，不在失败时退回模板。

1. **长度与表达**：简洁自然，围绕最相关的实际经历说明做过什么、服务谁及为何相关。仓库不设置首招字数硬上限；若平台有真实输入限制，宿主按已核实限制调整，不截断事实或替换已批准原文。
2. **事实与内容检查**：每项主张有已确认证据支撑，保留主体、职责、时间、范围和指标含义。不编造了解、称呼、背书或成果。数字和禁用词的既有程序内容检查继续执行；“0 到 1”与书名号内名称保留原有数字例外。
3. **场景适用性**：行业资质、术语与经历按当前 JD 的实际相关性选择，不强制每条使用同一产品锚点、背书、开头或收尾。偏好仅影响表达与选材，不确认新事实。
4. **独立复核**：复核完整正文的事实覆盖、目标相关性和表达；生成者自评不替代独立复核。事实不足或全文 JD 缺失时说明缺口，不产出假合格稿。
5. **一岗一条**：已有发送或查重发现已发的职位不再起草首招，转后续跟进。仓库继续核对职位、联系记录、数字、禁用词和证据。
6. **匹配档位**：正常首招面向强匹配与可能匹配，弱匹配和不匹配只列缺口，不提升档位。未知结果保持未评估；本人提供岗位不自动提升匹配。偏好分只在现有准入和排序策略内生效。

每条对外正文仍需本人按准确全文批准。后续问答式回复保留其独立规则；本次首招策略变更不改回复分级或平台节奏。

## 与审批的关系

消息是 `ApplicationPackage` 的一部分,参与审批摘要计算。消息任何一次改动都会使既有审批失效,必须重新审批。生成消息本身不构成投递意图。
