# 新职位来源接入阶梯

接入一个新平台时,**按顺序逐档评估,不得跳档**。越靠前的档位越稳定、越合规、维护成本越低。直接从最后一档开始,是这类项目最常见也最昂贵的错误。

每一档都要留下结论与依据,写进 [oss/source-manifest.yaml](oss/source-manifest.yaml) 与 [jd-sources.md](jd-sources.md)。

## 第 1 档 —— 官方 MCP 或官方 CLI

先查平台是否自己提供 MCP server 或命令行工具。

**判定为官方的条件**:域名属于该平台、或授权页在该平台域名下、或仓库归属该平台组织。社区项目取名像官方**不算**。

采信理由:官方通道有正式授权(通常是用户自行粘贴的 token),不触碰验证码与风控,字段有契约,平台改版时由官方维护。

**发现即采信,停止向下。** 以子进程或 MCP client 形式调用,不内联其源码。

> 已落地示例:猎聘的 `liepin-cli`,授权页在 `liepin.com/mcp/auth`,只使用其只读的 `job search`。

## 第 2 档 —— 平台官方开源仓库

平台自己在 GitHub 上开源的 SDK / 客户端 / 数据接口。

同样需要确认**归属**:仓库属于该平台的官方组织,而非同名个人账号。

采信前必须核对许可证。**无许可证 = 保留所有权利**,此时只能进程调用,不得复制代码。

## 第 3 档 —— 社区高星仓库

前两档都没有时,再看社区方案。**高星不等于可用**,必须逐项核对:

| 核对项 | 不可用的情形 |
|---|---|
| 许可证 | 无许可证;或声明与 README 矛盾(如 LICENSE 写 MIT、README 写"禁止商业用途") |
| 与本项目许可证兼容 | AGPL/GPL 与本仓库 Apache-2.0 不兼容,不得内联 |
| 取数手段 | 依赖指纹伪装、stealth 浏览器、代理或账号轮换、打码 |
| 是否违反平台条款 | 作者自己承认违反用户协议,或建议"注册专用小号" |
| 可剥离性 | 浏览器扩展、Electron 应用等无 CLI/无头入口的形态,取数逻辑绑死 DOM |

**只要命中"取数手段"或"违反平台条款"任意一条,整个仓库降为仅参考,不移植。** 星数再高也一样——这类项目星数往往正比于其激进程度。

可以借鉴的通常只有:字段结构、页面分区的观察、失败处理范式。这些写进研究笔记即可。

## 第 4 档 —— 公开页面解析

前三档都不可行,才考虑自行解析公开页面。

**开始之前必须先读 `robots.txt`**,并按本客户端实际使用的 User-agent 段判定。站方若已明确 `Disallow`,到此为止——那不是技术障碍,是站方用协议表达的意愿,不存在"绕一下"的空间。

允许解析时,遵守:

- 提取**两端有边界**(见 [jd-sources.md](jd-sources.md)),绝不让公司简介、防诈提示、推荐位混入 `jd_raw`
- 单条、由人触发,不做批量扫描
- 遇登录页、验证码、WAF、429/403 一律 `USER_INTERVENTION_REQUIRED`,不重试、不伪装、不换号换代理
- 境外平台(如 LinkedIn)的服务条款通常更严,批量访问的约束更紧

## 第 5 档 —— 如实告知做不到

四档都走不通时,**结论就是"这个来源接不进来"**。这是一个合法的终局,不是失败。

此时应当:

1. 明确告诉用户**哪一档因为什么原因不通**,给出可核验的依据(重定向地址、robots.txt 条目、许可证冲突原文)
2. 将该平台建模为 `GatedJobSource`,返回 `USER_INTERVENTION_REQUIRED` 并附人工路径,使链路完整、边界可见
3. 提供人工路径:用户自行在浏览器打开职位、复制 JD,经 `jobagent jobs ingest-jd` 提交
4. 若该平台仍有**被明确允许**的其他用途(例如公司页、口碑社区),单独评估,不与职位抓取混为一谈

**绝不做的事**:为了"把流程跑通"而降档绕行、伪造 `jd_raw`、或对用户隐瞒某个来源实际上没有接通。

## 记录要求

每接入或拒绝一个来源,都要留下:走到第几档、每一档的结论与依据、最终形态(官方通道 / 公开解析 / 门控暂停)、以及复核日期。平台改版与政策变更都会让结论过期。
