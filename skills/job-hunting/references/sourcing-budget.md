# Muse 寻源：反馈、薪资与阅读预算

只加载当前需要的职位与证据上下文。定时、模型、网页和私有持久化由宿主提供；本包不驱动浏览器。所有许可都只用于只读寻源，不授予联系招聘方或投递权限。

## 薪资

私有 CandidateFilterContext 默认 compensation_comparison=upper_bound：薪资区间与本人 minimum_compensation.minimum 及以上有重叠即可通过。以18k底线为合成示例，15–25k、15–18k、20–25k均接受，15–17k拒绝；金额来自本人配置，不设公共18k常量。区间下限低于底线不会单独导致拒绝。

只公布上限且达到底线可通过；只公布下限且已达到底线也可通过。只知道低于底线的下限、没有可确认的上限时保持 REVIEW。币种或周期不可比、周期缺失、薪资未知均待核查，不猜汇率或额外薪数。

lower_bound 仅在本人明确要求整个区间下限都达到底线时使用。已有配置若显式写了 lower_bound，须改成 upper_bound 才使用本次规则。既有 unstated_compensation_passes 是显式未知/未解析薪资例外，只有本人确认该例外才可开启；新配置保持 false。明确区间上限低于底线时，该例外不生效。

## 执行顺序与预算单位

1. 读取同版本规则、本人硬条件、基础查询、搜索学习快照与检查点；先验证私有持久文件及单实例保障。
2. 调用 sourcing-budget。创建 sourcing-start：每站每轮默认 query_limit=3、detail_limit=20，均是上限，不必用尽；查询最多6，详情最多50且不超过来源当日额度。来源每日详情上限继续 <=50。
3. 每次实际提交检索前，用新 attempt_id 调 sourcing-reserve，kind=query，记录准确 search_term。只有本次返回 allowed=true 才操作。检索调整也占一个查询额度；来源的会话总页数和翻页间隔限制仍同时有效，不按每个词重置。
4. 先观察列表，记录实际数量与去重/预筛结果。跨查询重复出现只保留一项待取详情，不因标题缺少某个技术词就认定 JD 不适合。每个查询的 sourcing-result 记录 outcome 和 listing_count；零结果明确写0。已有 search-log 仍记录查询历史、results 和 new，供轮换调度使用。
5. 只对需要补全文的岗位预占 kind=detail，注明 source_job_id、详情 URL，已知查询原文时同时带 search_term。预占后再打开详情。来源每日额度、轮次额度和宿主剩余执行时间取最紧约束；不按“每查询前10条”强制读全文。
6. sourcing-result 只追加结果 complete/partial/failed/gate/cancelled。失败、取消、重复读取同一岗位均消耗预占；不得更换 ID 假装幂等重放。相同 ID 重放返回 already_reserved 且 allowed=false，须查私有检查点，不再执行。
7. gate 结果使该站当天停止新的预占。旧轮次跨 Asia/Shanghai 当地日过期，次日创建新轮次。只读许可不解除登录、验证码、限流等停止条件。
8. 新完整 JD 沿用 import-observations → triage，保留 search_term；摘要标为未完成，不拼接为正文，不进入合格稿。
9. 保存私有轮次报告、准确查询、列表观察数、去重数、详情尝试数、完整/不完整数、过滤原因、新入库数与未完成项。没有新岗位仍保存报告；通知频率遵循本人设置。

程序时间由 CLI 生成，不接收宿主伪造时钟或每日上限。轮次额度创建后固定，重用同一个 ID 不能提高额度。新一轮仍共享每日详情消耗。

sourcing-budget 的 read_today = 记录的详情尝试 + 未精确计量的旧观测估算；legacy_unmetered 明示旧数据的局限。首次预占时保留旧观测估算，后续岗位保存不得将它退回。历史失败和重复读取无法从旧岗位表完整恢复，不补造；新链路必须遵循预占协议。当前库之间不共享额度，多个独立数据库不能被称作同一账号的全局限流。

## 有边界的调整（宿主执行政策）

保留用户基础查询、探索名额和冷却回访，不执行“上一轮搜过就永不再搜”。

- 零结果：在查询预算内，最多尝试一次别名或移除一个非必要软限定，保留角色与本人硬条件；把原查询与变更理由都记下。
- 重复较多：优先换尚未覆盖的组合；不要把同一岗位重复取详情当成新发现。
- 明显跑偏：增加一个有原文依据的角色或场景限定，不能将一次拒绝扩成全行业排除。
- 正文不全或解析失败：保留待补状态；遇平台门控立即停站，不靠扩词、换路径或重新登录重试。
- 预算或执行时间耗尽：保存未执行项，下轮继续，不声称搜索完成。

这组策略由宿主按真实页面执行，尚无新的自动组合/自适应调度引擎。现有 search-plan 仍是轮换与历史产出调度，不伪装成完整 ReAct 系统。

## 岗位与文案反馈分开

新 SearchSignal.kind=feedback，分别记录 job_preference（like/dislike/neutral）与 message_feedback（accept/revise/reject），至少一项。必须附本人原话、同一候选人、岗位、时间与 JD 引文。

“岗位合适但改招呼”可同时为 like/revise；仅接受或改写文案不产生岗位正负信号，也不擦除此前岗位选择。neutral 是明确撤回先前岗位偏好。拒绝薪资、地点或文案不能自动把行业/技术词写入 rejected_features；特征反例仍需本人明确点名。

学习输出仅调整软查询优先级。本人喜欢岗位、接受文案、阅读许可都不等于发送批准。最终准确全文和附件继续走既有逐项审批。


## 组合计划与真实执行

当前域快照/词库/组合按 [jd-knowledge.md](jd-knowledge.md) 加载；combinations只是计划，之后每次真实操作仍按本文预占。记录计划ID、实际query_hit/search_term、列表结果、详情完整性和来源引用；推荐/手工岗位不伪造查询。已发观察另读 [sent-tracking.md](sent-tracking.md)，状态报告不替代寻源报告，不自动改变预算或词库。
